> 사용자 실제 일지: 주간 메모에 이미지가 꽤 있음(2026-11-01) → 2절의 이미지 원인이 실사용과 맞음
> 요청(2026-10-31 사용자): ① 데이터 로딩·적재 방식, DB 파손 대비 백업·복구 정책 점검 ② 약 1년치 일지에서 주를 오가며 보고 고칠 때 메모리가 계속 늘어나는 문제 — 주 전환 시 필요한 것만 불러오도록 최적화

## 0. 요약

| 점검 | 결론 |
|---|---|
| 메모리 증가 | **재현됨. 원인 = 메모 이미지를 `data:` 주소(base64 문자열)로 그리는 방식.** 같은 1년치 일지에서 이미지를 빼거나, 이미지를 읽기만 하고 그리지 않으면 늘지 않는다(2절). 글 기록·주 전환·저장 자체는 새는 곳이 없다 |
| 데이터 로딩 | 주 전환은 이미 "그 주만" 읽는다(`getWeek` = 그 주 7일). 다만 한 번 넘길 때마다 **약 22번 조회**하고, 그중 절반가량은 바뀌지 않은 데이터(업무 목록·설정·태그·반복 규칙)를 다시 읽는다. 메모 이미지는 **원본 크기 전부**를 읽는다(메모 판이 접혀 있어도) |
| 쓰기 | 칸 단위 저장을 한 트랜잭션으로 묶음(`db_batch`)·실패 시 자동 롤백 — 문제 없음 |
| 백업 | 방식(`VACUUM INTO` → 임시 사본 검사 → 이름 바꾸기)은 안전. **빈틈 4가지**: ① 앱 안 복원 없음(손으로 파일 복사 안내뿐) ② 백업 시점이 "그날 첫 실행 + 종료"뿐이라, 며칠씩 켜 두거나 강제 종료되면 백업이 없음 ③ 사용 중 파손(디스크 오류 등)을 알아채는 길 없음 ④ 일지·백업이 같은 폴더(같은 디스크·OneDrive) |

## 1. 현재 구조

### 1-1. 데이터 경로
```
화면(Zustand 스토어: boardStore · noteStore · summaryStore · insightsStore)
  → JournalRepository(src/data/repository.ts) → SqlDriver
      실앱: tauri-plugin-sql(sqlx 연결 풀) + 여러 문장은 Rust db_batch(한 트랜잭션)
      브라우저 모드: sql.js(WASM, 메모리)
```
- 화면 스토어는 **지금 보는 주 1개**만 들고 있다(`cells`·`view`·메모 `doc`·`assets`). 주를 넘기면 통째로 바꾼다 — 예전 주가 쌓이는 캐시는 없다.
- 실행 취소 기록: 보드 50단계(칸 내용 사본), 메모 50단계(메모 문서 사본, 이미지 데이터는 포함 안 함) — 상한이 있어 계속 늘지 않는다.

### 1-2. 주 전환 1번에 일어나는 조회(`boardStore.loadWeek` + `noteStore.loadWeek`)

| 무엇 | 조회 수 | 바뀌는가 |
|---|---|---|
| 대기 중 저장 마무리(`flushAll`) | 0~n | — |
| 그 주 항목·업무 구간·연차·메모 문서(`getWeek`) | 5~6 | 주마다 |
| 반복 규칙(`listRecurrences`) | 2 | 거의 안 바뀜 |
| 설정(`getSettings`, JSON 해석) | 1~2 | 거의 안 바뀜 |
| 태그·업무별 태그 | 2 | 거의 안 바뀜 |
| 중요 업무 목록 + 이 주 완료(`refreshImportant`) — 각각 업무 목록을 다시 읽음 | 6 | 일부만 |
| 직전 기록일·내역(`refreshPrevDates`) | 2 | 주마다 |
| 메모 문서(**`getWeek`과 중복**) + 그 주 이미지 **원본 전부** | 2~3 | 주마다 |
| 떠나는 주 이미지 정리(`pruneNoteAssets`) | 1~2 | — |
| 이번 주만: 반복 채우기·무기록 제안 | +4~6 | — |
| 미래 주만: 반복 "예정" 미리보기 | +2 | — |

→ 약 22번. 실앱에서는 한 번마다 IPC(JSON 직렬화) 왕복이고, 이미지는 base64 글자로 Rust → JSON → 화면까지 몇 번씩 복사된다.

### 1-3. 쓰기
- 칸 하나 = `DELETE(목록에 없는 행) + UPSERT(행마다)`를 한 batch로. 입력 후 일정 시간 뒤 저장(디바운스), 주 이동·종료 전에 `flushAll`.
- 메모 문서 = 주 1행(JSON) 통째 저장, 이미지 = `note_asset` 행(base64 TEXT, 1장 최대 5MB).
- `journal_mode=DELETE`(파일 1개), 외래 키 켬. 스키마 변경은 전진 전용 + 직전 자동 백업.

### 1-4. 백업·복구 지금 동작

| 항목 | 지금 | 평가 |
|---|---|---|
| 방식 | `VACUUM INTO` 임시 사본 → `quick_check` → 이름 바꾸기 | ✅ 열린 DB에서도 일관된 사본, 반쯤 쓴 사본이 남지 않음 |
| 일일 | 그날 첫 실행 1회 + 종료 시 덮어씀, 최신 14개 | ⚠ 켜 둔 채 며칠 쓰면 그동안 백업 없음. 윈도우 업데이트 재시작·강제 종료·충돌이면 종료 백업도 없음 |
| 월간 | 그 달 첫 일일 때, 최신 12개 | ✅ |
| 수동·가져오기 전·업데이트 전·마이그레이션 전 | 자동 삭제 안 함 | ✅ (오래되면 쌓이기만 함 — 용량 표시 없음) |
| 시작 시 검사 | 일지 `quick_check` → 실패하면 "데이터 파일에 문제" 화면 | ⚠ 화면에는 [백업 폴더 열기]·[다시 시도]뿐, 복원은 손으로(파일 이름 바꾸기 안내) |
| 사용 중 파손 | 저장 실패 → "저장하지 못함 · 다시 시도" | ⚠ 디스크 오류·파손(`SQLITE_CORRUPT`/`IOERR`)도 같은 토스트 — 계속 쓰면 피해가 커질 수 있음 |
| 시작·종료 속도 | 시작 백업이 보드 표시 **전에** 끝나야 함, 종료 백업도 창 닫기 전 | ⚠ 이미지가 많아 일지가 커지면 시작·종료가 그만큼 느려짐 |
| 보관 위치 | 일지와 같은 폴더 `backups\` | ⚠ 같은 디스크·같은 OneDrive 폴더 — 폴더째 잃으면 백업도 없음 |
| 용량 | 일일 14 + 월간 12 = 일지 크기 × 최대 26개 | ⚠ 이미지 많은 일지(예: 100MB)면 백업만 2.6GB, 표시·경고 없음 |

## 2. 메모리 증가 측정

### 2-1. 방법
- **가상 1년치 일지**(실제 업무 아님): 업무 6개, 2025-11-03 ~ 2026-10-30 평일마다 업무 4개 × 항목 2~4줄(세부 항목·링크 포함) = 항목 4,427개, 52주 메모(글 상자 3개). 이미지 판은 주마다 이미지 2장(800×500 PNG, 장당 약 0.5MB) 추가 = 104장.
- 브라우저 모드(Chromium, Playwright)에서 `Alt+←` 50번 → `Alt+→` 50번 = 1왕복. 왕복마다 가비지 컬렉션 강제 후 **JS 메모리**(CDP)와 **프로세스별 메모리**(RSS)를 잰다. 편집 판은 주마다 칸 하나에 글을 써서 저장.

### 2-2. 결과(왕복마다, MB)

| 경우 | 시작 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 판정 |
|---|---|---|---|---|---|---|---|---|---|
| 글만 — 화면 프로세스 | 219 | 247 | 248 | 243 | | | | | ✅ 그대로 |
| 글만 + 매주 편집 — JS 메모리 | 21.4 | 25.4 | 25.6 | 25.8 | | | | | ✅ 그대로 |

### 2-3. 결론
- 늘어나는 것은 JS 메모리가 아니라 **이미지 그리기 쪽(브라우저 엔진이 `data:` 주소·풀어 놓은 그림을 붙잡고 있는 메모리)** 이다. 글 기록·저장·주 전환 로직은 새지 않는다.
- 실앱(WebView2)은 같은 Chromium 엔진이라 같은 현상이 예상된다. 여기에 실앱은 base64가 Rust → IPC JSON → 화면으로 여러 번 복사되는 비용이 더해진다.
- 단순히 `blob:`으로 바꾸면 증가가 브라우저 프로세스로 옮겨 갈 뿐이다(그리고 실앱 CSP `img-src 'self' data:`가 `blob:`을 막는다). **화면에 보이는 크기의 작은 그림만, 한 장씩 수명을 정해 해제**하는 쪽으로 바꿔야 한다(3절 O2).
- 측정은 리눅스 Chromium 기준이다. 회사 PC(WebView2)에서는 O1의 진단 표시로 같은 비교를 한 번 더 한다.

## 3. 개선 계획

### O1. 측정 도구·회귀 검사(먼저)
- `scripts/perf/`: 가상 1년치 일지 생성기(글만 / 이미지 포함) + 위 왕복 측정 스크립트(JS 메모리·프로세스 메모리·주 전환 시간·조회 수). `npm run perf:mem`.
- 수락 기준을 숫자로 고정: **이미지 판 7왕복 뒤 화면 프로세스 증가 ≤ 첫 왕복 값 + 30MB(멈춤)**, 주 전환 중앙값 시간, 주 전환당 조회 수.
- 회사 PC 확인용 진단: 설정 › 업데이트·정보에 [진단 정보] 접이식(현재 JS 메모리·일지 크기·이미지 수/용량·백업 폴더 용량·마지막 백업). 네트워크 없음, 복사 단추로 붙여 넣어 전달.
- CI: 짧은 판(글만 2왕복 + 이미지 2왕복)을 E2E 옆 별도 작업으로 — 기준을 넘으면 실패.

### O2. 메모 이미지 표시 방식(메모리 증가의 원인 해결)
1. **표시용 작은 그림(썸네일) 따로 두기**: 이미지를 넣을 때 원본과 함께 표시용(긴 변 800px, WebP)을 만든다. 메모 판은 표시용만 읽고, 원본은 [크게 보기]·[이미지로 저장]·스냅샷·엑셀 때만 그 한 장을 읽는다.
   - 스키마: 마이그레이션 `0007` — `note_asset`에 `thumb TEXT NULL`(전진 전용, 직전 자동 백업). 기존 이미지는 처음 볼 때 한 번 만들어 채운다.
2. **그리는 방식**: 5절 #1에서 고른다(추천 = a).
   - a) `<canvas>`에 **보이는 크기 × 화면 배율**로 그리고, 상자가 사라지면 캔버스를 비운다(CSP 그대로). 시제품 A의 "첫 왕복 +420"은 원본 크기 캔버스 때문 — 표시 크기면 1/4 이하.
   - b) 썸네일만 `data:`로 유지(가장 작은 변경, CSP 그대로) — 증가 폭이 이미지 크기에 비례해 줄 뿐 계속 늘 수 있음.
   - c) `blob:` 주소 — CSP `img-src`에 `blob:` 추가 필요(외부 주소는 아니지만 CSP 변경이라 승인 대상), 시제품에서 브라우저 프로세스 증가 확인.
3. 이미지 데이터를 스토어(`assets`)에 base64로 계속 들고 있지 않는다 — 그린 뒤에는 버리고, 필요하면 다시 읽는다.
4. **메모 판이 접혀 있으면 이미지를 읽지 않는다**(펼칠 때 읽기).

### O3. 주 전환 로딩 다듬기
- 거의 안 바뀌는 데이터(업무 목록·구간, 설정, 태그, 반복 규칙)는 **스토어 캐시** — 바꾸는 동작이 일어날 때만 다시 읽는다. 주 전환 조회 약 22 → **약 8**.
- 메모 문서 중복 조회 제거(`getWeek`이 메모를 읽지 않게, 메모는 noteStore만).
- `importantRows`가 매번 업무 목록을 다시 읽지 않게(캐시 사용). 중요 업무 목록은 중요 표시가 바뀔 때만.
- 빠르게 여러 주를 넘길 때(`Alt+←` 연타) 마지막 주만 그린다 — 앞선 불러오기 결과는 버림(지금은 순서대로 다 그림).
- 바로 옆 주(±1) 미리 읽기는 **하지 않는다**(메모리를 늘리는 쪽이라 이번 목표와 반대, 주 전환이 이미 충분히 빠름 — O1 측정값으로 다시 판단).

### O5. 앱 안 복원(data-spec 7-3 "M5" 약속 이행)
