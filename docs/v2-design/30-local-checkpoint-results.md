# 30. 요청 1~3번 연속 구현·로컬 검증 결과

2026-11-08 · `v2-design` · 제품1.23.0 / DB18 유지.

## 결과와 판정

사용자가 요청한 **1. 삭제·복합 명령, 2. 복원·장기 오프라인, 3. 로컬 PoC 마무리 항목**을 독립 모형에 구현했다. 기존152개와 신규62개를 합친 **214개 세부 시험이 모두 통과**했다. 실제 앱·클라우드·운영 DB는 변경하지 않았다.

| 요청 항목 | 이번 산출물 | 로컬 확인 |
|---|---|---|
| 1. 삭제·복합 명령 | lifecycle.mjs, 전송 큐/수신 확장 | 부모 삭제와 자식 수정/생성 경합, 본문/링크 일괄 저장, tombstone·원자적 수신 |
| 2. 복원·장기 오프라인 | recovery.mjs | 자산 포함 snapshot, 복원 전 사본, generation, 만료 cursor, 보존/정리·재동기화 아카이브 |
| 3. 마무리 검증 | 충돌 선택·구 대기 변환·이동 의존성, F1/F2·용량/종료 시험 | 기존 회귀 유지, 두 프로세스 경합, SQLite 용량 부족·SIGKILL·대용량 무결성 |

**판정: 이 로컬 기술 검증 범위의 기능 흐름은 확인했다.** 소규모 클라우드 검증의 설계/환경 준비로 넘어갈 근거가 생겼다. 제품 적용·정식 출시 판정은 아니며, 대용량 메모리 최적화와 실제 백엔드/Windows/macOS 검증은 남는다.

## 1. 삭제와 문서/링크 복합 명령

- delete-subtree는 부모와 하위 항목의 내용 버전 및 셀 버전을 함께 확인한다. 자식 수정이 먼저면 내용 충돌, 자식 생성이 먼저면 셀 충돌로 삭제를 거절한다. 삭제가 먼저면 이전 수정/생성을 수락하지 않고 로컬 내용을 복구 가능한 상태로 보존한다.
- 항목 삭제·세 종류 메모/자료 링크 정리·순서 재배치·tombstone·change log·cursor·멱등 결과가 한 트랜잭션이다. 같은 opId의 재요청으로 두 번 삭제하지 않는다.
- insert-child는 새 ID만 받아 부모의 하위 묶음 끝에 추가한다. 삭제한 ID는 retired_ids로 남겨 tombstone 정리 후에도 같은 generation에서 재사용하지 않는다.
- save-document는 주간/업무 보드의 JSON과 authoritative 링크 집합을 함께 검증·저장한다. 없는 항목/상자, 잘못된 자산 소유자, 중복 링크, 상자당20개 초과를 거절한다. 업무노트는 현재 스키마에 맞춰 링크 집합 없이 본문을 저장한다.
- 이 경로를 활성화한 문서는 범용 행 저장으로 우회하지 못한다. 직접 링크 행을 덮어쓰는 범용 명령도 거절한다. 실제 제품 서버의 인증/권한 정책은 별도다.
- 두 서버 프로세스에서 부모 삭제 대 자식 수정/생성, 문서/링크 동시 저장을 경합시켜 하나의 완결된 결과만 수락됨을 확인했다.

## 2. 자산 포함 복원과 오래된 기기

### Snapshot·복원

createSnapshot은 동기화된 레코드·자산 bytes·앱/원본DB/포맷 버전·generation/cursor·내용/셀 버전을 manifest와 함께 보존한다. 아직 미전송 변경이나 별도 복구 사본이 있으면 snapshot으로 이를 조용히 누락하지 않도록 거절한다. 이 snapshot은 앱 전체 폴더 백업을 대체하는 기능이 아니다.

restoreSnapshot은 hash/참조/자산을 검증하고, 현재 정상 상태를 pinned 사본으로 만든 뒤 새 generation에 복원한다. 레코드·자산·generation·복원 결과가 한 트랜잭션이다. 중간 실패/SIGKILL에서는 이전 상태를 유지하고, 응답 유실 재요청은 같은 복원 결과와 같은 사전 사본을 반환한다.

### 보관·정리와 만료

- compaction은 검증된 checkpoint snapshot이 있을 때만 수행한다. 명시한 floor까지 change log·멱등 결과·tombstone을 정리하고, 오래된 cursor/명령은 재동기화를 요구한다. 삭제 ID 예약은 유지해 자료의 무단 부활을 막는다.
- 자산 GC는 현재 레코드·snapshot·재동기화 아카이브의 자산을 보호한다. 대기 편집/복구 사본이 있으면 보수적으로 삭제하지 않는다. 손상된 보호본을 정상으로 간주해 삭제를 진행하지 않는다.
- snapshot 보관 정리는 미리보기 inventory hash를 받은 뒤 적용한다. 새 사본이나 pin 변경으로 계획이 달라지면 거절하고, pinned 사본은 개수보다 우선해 보존한다. 테스트의 keep 숫자는 시험 인자이며 실제 서비스 보관 정책을 확정한 값이 아니다.
- compacted floor보다 오래된 대기 명령을 새 버전으로 바꿔 자동 재전송하지 않는다. 캐시된 결과가 이미 정리되었다면 RESYNC_REQUIRED로 거절한다.

### 미전송 내용의 명시적 재조정

reconcile은 `archive-and-refresh` 선택을 요구한다. 기존 기준·working·대기/고정 명령·충돌·이동 의도와 자산을 recovery archive에 보존한 후 검증된 새 기준을 받는다. 예전 generation/cursor의 명령은 자동 재적용하지 않는다. 아카이브의 내용을 복구하려면 별도 확인 후 새 내용 초안이나 독립 사본으로 가져온다.

## 3. 충돌 선택·구 대기 변환·연속 이동

- resolveConflict는 사용자가 본 generation/revision이 유지됐는지 검사한다. 서버 유지, 내 내용 재제출, 이동 재시도, 독립 복구 사본을 지원하고 선택 전 내용을 history에 보존한다. 그 사이 제3수정이 들어오면 재검토를 요구한다.
- 삭제된 항목의 내 수정은 서버에 자동 부활시키지 않고 독립 사본으로 남긴다. 이 사본은 로컬 검토용이며 자동 동기화되지 않는다.
- 아직 전송하지 않은 예전 내용 초안은 명시적 선택·기준 일치·허용 필드 검사 후 새 초안으로 전환한다. 이미 고정된 명령이나 구조 변경은 조용히 변환하지 않고 아카이브/재동기화를 요구한다.
- enqueueMoveAfter는 이동 의도를 의존성 큐에 기록한다. 선행 이동이 수락된 뒤 새 셀 버전으로 후속 명령을 생성한다. 이미 만든 명령은 바꾸지 않는다. 선행 이동의 충돌/취소 시 후속 이동을 멈춘다.
- 후속 이동은 승격 전까지 대기 의도로 보존하며, 로컬 위치 투영은 현재 활성 이동에 적용한다. 취소/충돌한 의존성을 자동으로 다른 명령에 연결하지 않는다.

## F1/F2 계측과 한계

| 표본 | 데이터 | 최종 실행 | 프로세스 최대 RSS |
|---|---|---:|---:|
| F1 | 업무10·항목1,000·노트20·주간 보드4·업무 보드10·합성 자산20 |493ms|99,772KiB|
| F2 | 항목100,000·합성 자산200 ×256KiB =50MiB |30,772ms|1,193,380KiB (약1.22GB /1.14GiB)|

시간은 생성→전환→모형 가져오기→snapshot 검증 등을 포함한 단일 로컬 실행이다. F1은 내용/이동 동기화 표본도 포함한다. F2는 저장·hash·snapshot 무결성 시험이며, 10만 항목의 UI 조작·네트워크·실시간 반영 성능을 확인한 것이 아니다. 두 표본의 이미지는 PNG prefix를 가진 합성 저장 페이로드이며 이미지 렌더링 품질을 검증하지 않았다. RSS는 같은 stress worker의 누적 최고값이고 p95/SLA가 아니다.

초기 F2 검증에서 반복 전체 조회가 발견되어 문서/셀 검증을 한 번의 메모리 인덱스로 바꿨다. [개선 전 단회 기록](evidence/stress-before-index.txt)의72,817ms·1,776,020KiB에서 위 값으로 줄었으며 원본/결과 hash는 같다. **현재도 대용량 처리의 높은 메모리는 제품 적용 전 분할/스트리밍 최적화 과제**다. 무료 백엔드에서 이 Node 모형을 그대로 실행할 수 있다는 근거로 쓰지 않는다.

## 개발 중 수정과 상태

[초기 검증 기록](evidence/checkpoint-initial-validation.txt)을 보존한다. 개발 중 새 변환 경로의 누락 import를 ESLint와 시험으로 검출해 수정했다. 최종 코드는 ESLint·Prettier·diff 검사와214개 회귀시험을 통과했다.

기존 앱 소스·migration·package/lockfile·워크플로·제품 버전은 변경하지 않았다. SQL 행 wrapper와 가상 계정 라벨은 제품용 도메인/보안 구현이 아니다. 전체 문서 파서·기능 전수·실제 타이머/백오프·계정/기기 인증·Windows/macOS·실제 클라우드는 후속 단계다. P01~P22의 전체 환경 상태는 NOT_RUN을 유지한다.

**다음 단계는4번: 최종 백엔드·실제 계정/아시아 리전·SMTP·비용 상한·계정 복구 정책을 확정하는 것**이다. 그다음 실제 Auth/권한·DB/비공개 자산을 검증한다. 새 클라우드 자원이나 배포는 이번 작업에 포함하지 않았다.
