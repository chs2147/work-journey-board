## 2. 규칙(88문서 0절 그대로)

- **서로 다른 기록** = 각각 적용.
- **같은 기록의 겹치지 않는 칸** = 합침(세 갈래: 기준·이 기기·서버). 고친 시각(`updated_at`)만 다른 것은 겹침으로 보지 않고 늦은 시각.
- **같은 칸**, 또는 **문서**(주간 메모·업무 메모보드·업무노트)를 양쪽에서 고침 = 조용히 덮어쓰지 않고 **이 기기 것을 그대로 둔 채 충돌로 보존**. 고르기 전까지 그 기록은 보내지 않고, 다른 기록은 계속 동기화.
- 고르기: **이 기기 것**(서버 판을 기준으로 다시 보냄) / **서버 것**(서버 값을 적용) / **둘 다 보존** — 업무 기록·업무노트는 내 것을 새 항목으로, 주간 메모·메모보드는 상자를 합침(같은 상자를 둘 다 고쳤으면 내 것을 새 상자로 옆에).
- **지우기** = 지움 표시로 전파(받은 쪽에서 행 삭제). 지운 기록을 다른 기기가 고쳤으면 충돌.
- **받은 것을 다시 보내지 않음**: 적용 중에는 대기열 트리거를 끈다(`applying=1`). 앱의 트리거(상태 이력 등)도 적용 동안 잠시 빼고 그대로 다시 만든다(받은 기록이 이력을 새로 만들지 않게). 외래 키는 묶음 끝에 확인. 행 바꾸기는 `INSERT … ON CONFLICT DO UPDATE`(REPLACE는 자식 행을 지움).
- **이 기기 전용 값**: 장치 설정(백업·AI·화면 — 칸반 열 순서·아이콘만 공용)과 다시 지정한 폴더 경로는 받아도 이 기기 것을 지킨다. 그래서 공간을 열 때 앱이 쓰는 이 기기 설정은 보내지 않는다(대기열에서 지움).
- **응답 유실**: 보내기 전에 요청(번호·내용)을 일지에 적어 두고, 결과를 못 받으면 다음에 같은 번호로 다시 → 서버가 같은 결과(한 번만 적용).
- **새 그림**: 해시가 처음이면 새 객체 ID → 신고 → 예약 → 올리기 → 참조를 담은 기록 push(서버 DB에 본문 없음). 받은 기록의 그림은 캐시 → 없으면 받아서 해시 확인.

## 4. 시험

- 단위 `spaceSync.test.ts` 7개: 행 사상 = 이관 기록, A 고침 → B 받음(재적용 없음), 다른 칸 합침·같은 칸 충돌·이 기기/서버/둘 다, 문서 충돌 → 상자 합치기, 지움 전파·새 그림(서버 기록에 본문 없음, 받은 쪽 같은 그림), 오프라인 대기·응답 유실 재전송 한 번만, 세 갈래 합치기.
- Rust `space_sync` 3개(가짜 gateway): 동작·모양 검사, 신고 → 예약 → 올리기·캐시·이미 ready, 받기 캐시·해시 거절.
- E2E `online-spaces`: 고침 → 대기열 → "동기화됨", 다른 기기 변경 → [지금 동기화] → 화면, 오프라인 표시.
- 발견·수정: 대기열 트리거의 `INSERT OR REPLACE`가 바깥 upsert 안에서 실패 → 트리거도 upsert(E-1 일지는 열 때 트리거를 새로 만듦).

### 5-2. 2차 실기 의견(2026-11-16) — 서버 호출 수·종료 안내

- **무료 플랜 영향(추정)** — 공개 Free 기준: Edge Function 50만 회/월, DB 500MB, egress 5GB([23](23-supabase-free-tier-readiness.md)). 서버 호출은 gateway 1회 = 함수 1회.
  - 받기: 창이 활성일 때 30초마다 → 하루 4시간 활성 × 기기 2대 × 22일 ≈ **2.1만 회/월**.
  - 보내기: 고친 뒤 1초 쉬면 1회 → 하루 300번 쉬며 고침 × 22일 ≈ **0.7만 회/월**(이번 수정 전에는 보낼 때마다 받기도 해서 2배).
  - 합계 ≈ 2.8만 회/월 = 한도의 **약 6%**(개인 1명). 시험 5명이면 약 30%. DB는 지금 값만 두고(고친 이력 X), 처리한 요청 기록이 하루 수십 KB씩 늘어 한 달 수 MB. 받기 응답은 대부분 비어 있어(약 200바이트) egress는 미미.
  - 개발 서버 실측(2026-11-16): 보내기 13회·바뀐 기록 1건·동기화 표 합계 약 0.8MB, DB 전체 16MB.
  - 운영 전(G단계): 받기 주기를 늘리거나(06문서 5분) 서버 알림 방식 비교, 처리한 요청 기록 보관 기간(예: 7일) 정리.
- **이번 수정**: 고친 뒤에는 **보내기만**(받기는 30초 주기·창 복귀·[지금 동기화]) → 편집으로 생기는 호출을 반으로.
- **종료가 늦던 원인**: 종료할 때 앱의 "종료 백업"이 일지 전체를 복사·검사했는데, 온라인 공간에서는 그 사본이 메모리에만 남아 꺼지면 사라진다(쓸모없는 몇 초). 온라인 공간에서는 자동 백업(첫 실행·종료)을 하지 않는다(`Platform.ephemeralBackups`) — 보관은 이 기기 일지 파일 + 서버.
- **종료 중 안내**: X·[목록으로]를 누르면 즉시 화면 전체를 막고 "저장하고 종료하는 중…"(목록으로는 "저장하고 닫는 중…")을 보인다. 클릭·입력이 막혀 동작하지 않는 것처럼 보이지 않게.

### 5-3. 3차 실기(2026-11-16) — 안내 없이 기다리다 종료 → 닫기를 Rust가 주도

- 실기: 5-2 판에서도 "종료하는 중" 안내가 보이지 않고 한참 뒤 종료(= 15초 안전장치가 끝낸 것으로 판단). 화면(JS)의 닫기 처리(`onCloseRequested`)가 Windows 실기에서 기대대로 돌지 않았다 — 로그가 없어 어느 줄인지는 특정하지 못함.
- 구조 변경(`src-tauri/src/preview_close.rs`):
  1. 메인 창 닫기 요청을 Rust가 받는다. 열린 온라인 공간 일지가 없으면 바로 종료.
  2. 있으면 닫기를 막고 화면에 `preview-closing` 신호 → 화면은 **React를 거치지 않고 즉시 DOM 덮개**("저장하고 종료하는 중…", 클릭·키 차단) → 동기화 멈춤 → 저장(2.5초 제한) → 일지 닫기(1초) → `preview_exit`.
  3. Rust는 화면 응답 또는 4초 뒤 열린 공간 일지를 닫고(각 1.5초 제한) 종료. 어떤 경우든 **8초 안전장치**(15초 → 8초).
- 진단: 단계 이름·경과 ms를 Preview 폴더 `close-trace.log`에 남긴다(덮어씀, 기록 내용 없음). 다시 늦으면 이 파일로 어느 단계인지 본다.
- 실기(2026-11-16, `9e0897f`): 바로 종료 확인.
- 정식판(Classic)은 이 경로를 쓰지 않는다 — 동기화·온라인 공간 일지(sqlx 연결)가 없고 닫기는 기존 `tauri.ts`(입력 저장 → 종료 백업 → 창 닫기) 그대로.

## 6. 남은 것 · 알려진 점

- 실기(m1-check 7-50): 두 기기 동시 편집·오프라인 편집 후 합치기·충돌 고르기·그림.
- 받은 변경 반영 = 일지 다시 열기(화면 한 번 새로 그림). 저장소별 부분 새로 고침은 후속.
- 지움 표시 보관 한도·오래 오프라인 후 전체 다시 받기, 공유·팀 편집은 G단계 이후.
- 운영 주기(5분, 비용 우선)는 G단계에서 다시.
