# 2. 저장 모델·동기화 방식·오프라인 전환

1차 범위는 **개인 여러 기기 동기화로 사용자 확정(2026-11-08)**. 공간은 한 계정이 소유하며, 타 계정 초대/공유/팀 공동 편집은 후속 범위다. 여러 본인 기기의 동시·오프라인 수정에 대한 충돌 처리는 1차에 포함한다.

## 2.1 기존 DB 통합/분리 결정

| 안 | 장점 | 문제 | 판단 |
|---|---|---|---|
| V1과 V2가 같은 SQLite를 직접 공유 | 복사 불필요 | 구 앱이 outbox 없이 저장·삭제하면 서버 상태와 어긋남. v18 JSON/로컬 revision만으로 다중 기기 충돌 해결 불가 | 비추천 |
| V2 전용 DB와 모델을 완전히 별개 개발 | 독립 개발 | 두 모델·가져오기·기능 버그가 계속 분기, 웹/모바일 확장 비용 증가 | 비추천 |
| **공통 도메인·V2 로컬 스키마 + 서버 모델, V1 파일은 복사 전환** | 기능 규칙 재사용, 원본 보존, 장치별 저장소에 맞춤 | 변환기·버전 계약·검증 작업 필요 | **추천** |

V2 desktop도 로컬 우선 SQLite를 사용한다. 서버 PostgreSQL은 동일 파일/동일 DDL이 아니라 공통 타입·명령·검증·식별/관계 계약을 따른다. 로컬 DB schema, 서버 schema, API protocol, 문서 JSON format, snapshot format, app semver는 각각 별도 버전이다. 다음 로컬 스키마 번호는 구현 시 기존 릴리스 마이그레이션과 충돌하지 않게 결정한다.

V1 원본과 V2 사본은 전환 뒤 독립 데이터다. V1에서 계속 기록해도 V2 서버에 자동 반영되지 않으며, 추가 가져오기는 중복/충돌을 검증하는 별도 절차로 다룬다.

공간별 로컬 metadata DB1개에 outbox/inbox/cursor/conflict를 둔다. **후속 사용자 요구 반영:** 기존 V1/로컬 전용 공간의 DB 포함 이미지 계약은 유지하며, 새 V2 온라인 연결 공간만 DB 밖 binary 자산 저장으로 분리한다. 온라인 공간의 DB 단독 복사는 완전 백업이 아니다. 원본 보존·독립 앱/배포·오프라인 실물·중복 제거/보관 정책의 최신 설계는 [46문서](46-local-compatibility-image-storage.md)를 따른다.

## 2.2 세 가지 방식 비교

| 방식 | 작동 | 오프라인/충돌 | 운영 부담·용도 |
|---|---|---|---|
| **1. 변경분 즉시 전송 + 다른 기기에 알림** | 로컬 저장 즉시 큐, 짧은 묶음 전송, 서버 확정 후 상대 장치가 변경분 수신 | 연결 끊겨도 로컬 저장. 재연결/동시 수정은 충돌 처리 필요 | 가장 높은 신선도. 지속 연결·관측·재시도 필요 |
| 2. 주기 동기화 | 같은 변경 큐를 예: 5분마다·실행/포커스 시·수동 버튼으로 전송 | 두 기기의 변경이 더 많이 겹칠 수 있음. 실시간과 같은 충돌 모델 필수 | 배터리/트래픽 절감, 주기/마지막 수신 시각 안내 |
| 3. 온라인 백업만 | 로컬 스냅샷을 버전별로 업로드, 사용자가 고른 백업으로 복원 | 다른 기기의 변경을 자동 병합하지 않음. 복원은 현재 로컬 변경을 보존한 뒤 별도 공간/명시적 교체 | 가장 단순. 기기간 최신 상태 유지와는 다른 목적 |

**추천 최종안: 공간별 `로컬 전용 / 온라인 백업 / 동기화` 선택. 동기화의 전달 정책은 즉시/주기.** 모든 공간을 자동 연결하지 않는다. 1·2는 같은 프로토콜로 구현하고 설정만 바꾸되, 3은 별도 백업 스트림이다. 초기 검증은 백업/복원 → 수동·주기 증분 → 즉시 증분 순서가 위험을 줄인다. 이는 출시 순서 제안이며 3번 방식을 실시간 동기화로 광고하지 않는다.

‘실시간 저장’은 **매 입력을 서버에서만 저장**한다는 뜻이 아니다. 로컬 트랜잭션을 먼저 완료하고 0.5~2초 수준의 전송 묶음을 목표로 한다. 상대 화면 반영 2~5초는 일반 연결에서의 PoC 목표이며 SLA 확정값이 아니다. 모바일 OS가 앱을 정지한 동안은 즉시 갱신을 보장하지 않고 재개 시 수신한다.

## 2.3 공간·항목 식별과 범위

- 서버가 발급한 `cloudWorkspaceId`, 안정된 사용자 `accountId`, 설치별 `deviceId`를 분리한다. 이름·이메일·폴더 경로는 식별자가 아니다.
- 현재 로컬 공간 메타데이터와 별개로 V2 `localWorkspaceId`와 cloud binding을 기록한다. 같은 이름의 공간을 자동 합치지 않는다. ‘기존 온라인 공간 연결’과 ‘새 온라인 공간 생성’을 명확히 구분한다.
- 서버 키는 `(cloudWorkspaceId, entityType, entityId)` 범위를 기본으로 한다. 주간 메모 `2026-W45`처럼 반복되는 키도 다른 공간의 데이터와 섞이지 않는다.
- 기존 UUIDv7은 가능한 한 보존하되 시간값을 충돌 순서로 믿지 않는다. 서버 커밋 sequence가 수신 순서이고 클라이언트 시계 오차는 정합성에 영향이 없어야 한다.
- 로컬 DB 복사/복원 시 deviceId·인증정보·outbox opId를 무작정 복제하지 않는다. 같은 공간의 복원과 새 공간 복제를 나누어 binding/큐를 재구성한다.

## 2.4 무엇을 동기화하는가

| 범주 | 정책 |
|---|---|
| 업무·태그·기간·주간/데일리 항목·중요/완료·반복 | 동기화. 부모/자식·참조·정렬·반복 발생 키의 중복 방지 포함 |
| 주간 메모·Cabi.NET 노트/보드·관계선·지식 카드 | 동기화. 문서 JSON과 연결 테이블을 같은 정합성 단위로 처리 |
| 이미지 원본·참조 관계 | 별도 비공개 blob 업로드 완료를 확인한 뒤 문서 revision 공개. 섬네일은 재생성 가능한 캐시 |
| 주간 요약 | 사용자 확정/수정본은 데이터로 보존. 재계산 가능한 지표·인사이트 캐시는 재생성 |
| 휴일 설정·업무용 날짜·사용자 정렬 | 업무 의미가 있는 값은 동기화. UI 언어와 타임존으로 원래 날짜를 변경하지 않음 |
| PC 폴더 경로·바로가기·기기별 로컬 파일 | 원본 디렉터리를 자동 업로드하지 않음. 자료 카드 메타데이터와 기기별 경로 binding 분리. 웹/모바일은 ‘이 기기에서 연결되지 않음’ 표시 |
| 원문 링크 URL | 업무 데이터로 분류하되 URL 토큰/사내 주소의 업로드 범위 사전 안내. 자동 사이트 방문·미리보기 수집 없음 |
| 언어·창 위치·확대/툴바·최근 PC 경로 | 기기 설정. 계정 기본 선호와 공간 콘텐츠를 구분 |
| 인증 토큰·로컬 백업 경로·실행 취소 스택·검색 인덱스 | 동기화 제외. 보안 저장/로컬 생성, 서버 변경 이력은 로컬 undo와 별도 |

현재 로컬 이미지의 base64 TEXT 저장은 영구 유지한다. 명시적 온라인 사본 생성 때만 새 사본에서 binary 추출/Blob 이관·hash/size/mime를 검증한다. 온라인 DB/JSON/outbox/snapshot에는 이미지 본문을 넣지 않는다. 원본 이미지가 Blob과 별도로 남는 것은 의도된 안전 복제이며 삭제 대상이 아니다. 객체 hash가 같아도 접근 권한은 공유되지 않는다. 계정 간 존재 여부가 유출되는 전역 dedup API는 제공하지 않는다.

## 2.5 로컬 우선 프로토콜 초안

```text
사용자 편집
  → 로컬 데이터 + outbox를 한 DB batch에 기록
  → 로컬 저장 완료 표시(온라인 동기화 완료와 분리)
  → blob 업로드/확정 → batch push
  → 서버 권한·버전 검사 → 데이터와 change log를 한 트랜잭션으로 커밋
  → ack/서버 revision → 로컬 큐 확인 처리
  → 상대 기기 변경 알림 → pull(cursor) → inbox 적용+cursor 갱신을 한 batch에
```

전송 단위 예시(미확정):

```json
{
  "protocolVersion": 1,
  "workspaceId": "cloud-uuid",
  "deviceId": "install-uuid",
  "opId": "unique-operation-uuid",
  "batchId": "atomic-business-command-uuid",
  "entityType": "cabiNote",
  "entityId": "note-uuid",
  "baseRevision": 17,
  "action": "update",
  "formatVersion": 1,
  "payload": { "title": "사용자 원문", "content": {} }
}
```

- 로컬 Cabi revision(자식 창 CAS), 네트워크 server revision, cursor, formatVersion을 다른 필드로 관리한다.
- `(workspace, device, opId)` 멱등 키를 서버가 보관한다. ack 유실/재전송은 같은 결과를 반환하며 operation 보존 기간이 끝났으면 오래된 클라이언트는 강제 재동기화한다.
- change log sequence는 공간별 단조 증가. 페이지마다 인증/권한 확인하고 클라이언트가 요청한 workspace 필드를 그대로 신뢰하지 않는다.
- 서버에서 적용한 내용을 다시 로컬 outbox로 생성하지 않는다. outbox/inbox의 applied 상태와 cursor를 데이터 변경과 원자적으로 묶는다.
- 네트워크/서버 장애는 지수 backoff+jitter. 인증 만료·권한 박탈·용량 초과·버전 미지원·충돌은 무한 재시도하지 않고 상태를 구분한다.
- 정합성 단위는 테이블 한 행과 같지 않을 수 있다. 예: 보드 JSON 변경+객체 링크 제거, 항목 삭제+연결 정리, 반복 항목 생성은 명령 batch로 적용한다.
- 서버는 영구 change log 무한 보관 대신 snapshot+cursor 하한을 운영한다. cursor가 만료된 기기는 미전송 outbox를 먼저 보존한 뒤 snapshot 기준으로 재조정한다. 단순 로컬 DB 삭제/재다운로드로 처리하지 않는다.

## 2.6 충돌·삭제·복원

**모든 텍스트를 마지막 저장본으로 덮어쓰는 LWW는 채택하지 않는 방향을 추천한다.**

- baseRevision 일치: 적용. 서로 다른 독립 레코드: 독립 적용. 단순 필드의 공통 조상이 있고 겹치지 않는 수정만 검증된 3-way 병합 허용.
- 같은 노트/같은 보드 JSON 동시 수정: 초기에는 문서 단위 CAS+양쪽 사본 보존·충돌 목록·사용자 선택. 다른 객체를 편집했다고 가정해 JSON을 임의 병합하지 않는다. 문서 내용과 참조 링크도 같은 충돌 단위로 관리한다.
- 같은 문장을 여럿이 동시 편집하는 UX가 필요하면 stable block/object ID + CRDT를 별도 PoC한다. 개인 다기기 동기화와 팀 공동 실시간 편집을 같은 난이도로 산정하지 않는다.
- 삭제는 tombstone과 삭제 revision으로 전파한다. 삭제된 부모에 신규 자식을 만들거나 수정하는 요청은 충돌로 보존하고 조용히 버리지 않는다. 구 기기의 재접속으로 삭제 항목을 부활시키지 않는다.
- tombstone·멱등 키 보관 하한과 최대 오프라인 기간을 같은 정책으로 설계한다. 장기 오프라인 기기는 전체 재동기화를 요구하고 미전송 자료는 별도 복구 사본으로 남긴다.
- 서버 백업으로 복원은 이미 동기화된 삭제/수정을 되돌리는 새 generation 작업이다. generation을 바꾸고 모든 기기가 새 snapshot을 기준으로 재조정하도록 한다. 이전 generation의 outbox를 그대로 적용하지 않는다.
- 로컬 undo는 서버 revision 역행이 아니라 현재 revision에 대한 새 명령이다. 다른 기기 변경과 충돌할 수 있음을 안내한다.

## 2.7 기존 공간의 온라인 전환

원본 상태: **local 영구 유지**. 새 사본 상태: `new-copy → preflight → snapshot-prepared → upload-staging → verify → connected`. 실패/취소는 새 사본의 미완료 staging에서 처리하며 원본의 mode/DB/이미지를 변경하지 않는다. [56 철칙](56-local-permanence-copy-migration.md)이 우선한다.

1. 사용자가 원본 공간의 **온라인 사본 만들기**를 실행하고 별도 ID/위치의 새 공간 연결 방식을 선택한다. 계정·저장 리전·업로드 범위·폴더 경로 제외·보관 정책을 확인한다.
2. 모든 자식 창 flush와 작업 대기를 완료하고 일관된 snapshot을 만든다. 원본 V1 DB/기존 백업을 보존하고 V2 대상 파일에 복사·전진 변환한다. 실행 중 DB 파일을 임의 복사하지 않는다.
3. 새 cloudWorkspaceId에 숨겨진 staging generation을 만든다. count/참조/문서 포맷·자산 hash 목록과 snapshot manifest를 작성한다. 기존 DB에 들어 있는 불필요한 캐시/PC 경로를 통째로 올리지 않는다.
4. 분할·재개 가능한 업로드, 매번 hash/size 확인. 다른 기기는 이 staging을 정상 공간으로 볼 수 없다. 완료 전 서버에 연결 성공으로 표시하지 않는다.
5. 서버가 레코드/이미지/참조·manifest를 검증한 뒤 generation을 공개한다. 로컬 binding과 초기 cursor를 확정한다. 최초 업로드 중 새 온라인 사본의 편집만 그 사본의 snapshot 이후 outbox에 쌓는다. 원본 로컬 공간의 이후 편집은 자동 수집/업로드/병합하지 않는다.
6. 두 번째 기기는 같은 계정으로 온라인 공간을 골라 **새 로컬 파일**에 내려받고 전체 검증 후 활성화한다. 같은 이름의 로컬 공간을 덮어쓰지 않는다.
7. 실패/취소 시 원본 보존, staging 만료 정리. 연결 해제는 먼저 미전송 변경을 알려주고 로컬 독립 사본을 보존한다. 원격 자료 삭제와 로컬 연결 해제를 다른 동작으로 제공한다.

원본 계속 사용: 원본 로컬 공간은 이관 전후 그대로 사용 가능하며 롤백/복구가 필요하지 않다. 새 온라인 공간에 추가한 내용은 독립 자료이고 자동 역변환하지 않는다. V2 변경의 구조화 export/별도 로컬 사본을 보존한다. 클라우드 복구를 위해 실행 중인 V1 DB를 V2 DB와 동시에 공유하지 않는다.

## 2.8 화면 상태 초안

공간별 ‘저장됨’은 로컬 저장 상태. 옆에 별도로 `로컬 전용 / 온라인 백업(마지막 시각) / 동기화 중·대기 N건 / 동기화됨 / 연결 끊김 / 충돌 N건`을 표시한다. 마지막 전송뿐 아니라 마지막 수신 시각을 확인할 수 있게 한다.

관리 화면: 공간과 계정·리전 → 연결 기기 → 즉시/주기 → 대기/충돌 → 백업/복원 → 연결 해제 순서. 상세 화면은 ‘내 기기 사본 / 서버 사본 / 둘 다 보존’을 비교하고, 선택 전 자동 보존본을 남긴다. 이 단계는 동작 흐름 초안이며 최종 GUI 시안은 정책 선택 후 작성한다.
