# 5. 온라인 저장·보호 정책 — 1차 구체안

2026-11-08 (KST) · `v2-design` · 설계 단계

사용자 추가 확정: **회사 정책과 별개로 개인용/외부 서비스용 구축이 가능해야 하므로 퍼블릭 클라우드 저장 가능 모델을 기본 전제로 한다.** 회사 정책 확인을 전체 프로젝트의 선행 조건으로 삼지 않는다. 실제 회사 자료 업로드 허가나 실제 클라우드 계정 생성/전송을 승인받은 것은 아니다.

## 5.1 제품의 기준과 공간 선택

- 기본 운영 모델: 서비스가 제공하는 클라우드에 개인 계정의 공간을 저장하고 여러 본인 기기에서 이용한다. 팀 공유·공동 편집은 후속이다.
- 기존 완전 로컬 사용도 유지한다. 온라인판에서도 새 로컬 공간을 만들거나 기존 공간을 열었다는 이유만으로 업로드하지 않는다. 사용자가 해당 공간을 온라인 백업 또는 동기화에 연결할 때 시작한다.
- 순수 로컬 프로필은 계정 없이 동작하고 네트워크 모듈/권한을 분리한다. 온라인판의 ‘로컬 전용 공간’은 콘텐츠를 전송하지 않지만, 로그인한 앱의 계정 관리 통신까지 외부 통신0이라고 표기하지 않는다.
- 회사의 제약이 있는 사용자는 로컬 전용 또는 향후 사내 호스팅을 선택할 수 있다. 사내 호스팅 개발을 개인용 퍼블릭 클라우드 서비스 출시의 필수 조건으로 두지 않는다.
- ‘기본 모델’은 설계 전제다. 사업자·리전·암호화·보관 수치는 아래 추천을 검토해 확정한다.

## 5.2 저장 위치와 데이터 경로

| 구분 | 1차 추천 | 검토·계약에 필요한 점 |
|---|---|---|
| 업무 레코드·문서·변경 이력 | 단일 primary region의 관리형 PostgreSQL | 지역 가용성, PITR, 테넌트 정책, DB 연결/연산 비용 |
| 이미지·스냅샷 | 같은 리전의 비공개 객체 저장소 | 서명 URL·다운로드 비용·버전/삭제·해시 검증 |
| 인증·세션 | 관리형 인증 + 서비스의 accountId | 인증 메타데이터 저장 국가, 계정 복구·기기 회수 |
| 이메일 인증·기기 알림 | 신뢰할 수 있는 메일 공급자 | 이메일 주소·인증 링크가 전달되는 국가/하위 처리자 |
| 운영 로그·모니터링 | 원문 제외, 필요한 식별자 최소화 | 로그 수집/백업 위치, 운영자 접근·보관 기간 |
| 백업/재난 복구 | 우선 같은 리전·분리 권한 | 지역 장애 대응과 국가 간 복제는 별도 결정 |

초기 리전은 한국 사용자 지원을 고려해 서울 등 아시아 리전을 우선 비교하되 아직 확정하지 않는다. 한국어·영어 지원이 곧 한국/미국 이중 데이터 저장을 뜻하지 않는다. 영어 사용자도 동일 서비스에 가입할 수 있다.

**모든 데이터가 한국에만 남는다고 홍보하려면** 업무 DB뿐 아니라 Auth·이메일·로그·백업·지원 도구의 데이터 흐름까지 확인해야 한다. DB 소재지만으로 해당 약속을 하지 않는다. 다중 리전은 계정/공간에 명시적으로 배정하며 성능을 이유로 자료를 몰래 다른 국가로 복제하지 않는다.

## 5.3 암호화 비교와 추천

| 안 | 사용자에게 제공되는 보호 | 서버가 할 수 있는 일 | 부담·제약 |
|---|---|---|---|
| **A. TLS + 서버 저장 암호화 + 엄격한 권한 / MVP 추천** | 전송·저장 보호, 계정/공간별 격리 | 허가된 서버 처리에서 평문 접근 가능. 검증·검색·복구 운영 가능 | 운영자/서버 침해까지 막는 E2EE는 아님 |
| B. 클라이언트 E2EE | 서버는 암호문 저장, 복호 키는 사용자가 관리 | 암호화된 본문 검색/검증·미리보기 제한, 일부 메타데이터만 검사 | 기기 키 전달·웹 키 보관·복구 키·분실·공유 설계가 추가 |
| C. 자체 호스팅·고객 관리 키 | 운영 위치/주체의 통제 확대 | 배포/키 구조에 따라 다름 | 자체 호스팅이나 고객 키 사용만으로 E2EE가 되지 않음 |

**추천 초안:** 개인 다기기 MVP는 A로 시작하고 보호 범위를 정확히 안내한다. E2EE가 제품의 핵심 요구라면 B를 처음부터 선택하고 일정·검색·복구 범위를 다시 산정한다. 나중에 켜는 스위치 하나로 바꿀 수 있다고 설계하지 않는다.

A의 운영 경계:

- DB/객체 저장소 모두 비공개. 클라이언트에는 관리자·서비스 역할 키를 제공하지 않는다.
- API와 DB 정책에서 accountId → membership → workspace → 객체 접근을 확인한다. 문서 ID·이메일을 아는 것만으로 접근할 수 없다.
- 운영자 접근은 최소 권한·기간 제한·감사 기록을 두고, 사용자 원문을 로그·분석 도구에 기본 전송하지 않는다.
- TLS 인증서 검증을 끄지 않고, 토큰은 OS 보안 저장소 또는 웹 HttpOnly 세션에 둔다. 공간 백업에 로그인 자격증명을 포함하지 않는다.
- 계정 복구가 본문 복구에 미치는 영향을 명시한다. A는 서버 권한으로 복구가 가능하지만 B는 사용자 복구 키 없이는 운영자가 복호를 보장할 수 없다.

## 5.4 고객 백업·서비스 복구·보관 초안

세 가지를 구분한다: ① 사용자 공간의 온라인 백업, ② 동기화 공간의 시점 복구본, ③ 서비스 전체 장애 대응용 운영 백업/PITR.

| 정책 | 추천 기본값(검토용) | 실패/용량 초과 시 |
|---|---|---|
| 온라인 백업 전용 공간 | 앱이 실행·연결된 동안 하루1회, 최근30일 | PC가 꺼져 있으면 백업하지 못함. 다음 실행/연결 시 재시도하고 마지막 성공 시각 표시 |
| 동기화 공간 복구본 | 서버가 수락한 상태 기준 하루1회, 최근30일 | 미전송 로컬 변경은 포함되지 않음. 마지막 서버 revision 기록 |
| 수동 보존본 | 자동 보관과 구분, 최대10개 초안 | 한도 도달 시 사용자가 교체/삭제할 항목 선택. 임의로 모두 정리하지 않음 |
| 전체 보관 용량 | 요금·평균 자산량 PoC 후 결정 | 최신 정상 보존본을 보호하고 신규 백업 보류/용량 안내. 현재 업무를 삭제해 공간을 확보하지 않음 |
| 운영 재난 복구 | DB/객체의 일관된 백업과 실제 복원 훈련 | RPO/RTO·지역 장애 보장은 예산/시험 후 확정 |

하루1회·30일·10개는 서비스 약속이 아니라 설계 추천값이다. 최초 연결 시 초기 보존본을 만들고 중요한 전환/복원 직전에는 별도 안전 사본을 남기는 방향이다. 자동 정리 대상은 정책에 맞는 보존본이며, 현재 문서/복원 중 generation/참조 중인 자산을 지우지 않는다.

동기화 change log는 백업과 다르다. 로그 정리 기간과 장기 오프라인 지원 한도를 함께 정하고, 한도를 넘은 기기는 미전송 자료를 보존한 뒤 재조정한다. 현재 단계에서 기간을 임의 확정하지 않는다.

## 5.5 계정·삭제·서비스 종료 경계

- 탈퇴, 원격 공간 삭제, 이 기기 연결 해제, 기기 세션 회수는 각각 다른 절차다.
- 사용자가 언제든 표준 내보내기/로컬 독립 사본을 받을 수 있게 한다. 서버 장애나 구독 상태가 로컬에서 이미 저장한 업무를 읽지 못하게 만들지 않는다.
- 저장 한도 초과 시 신규 서버 업로드를 제한하더라도 로컬 편집은 유지한다. 서버 수락이 안 된 변경을 ‘동기화 완료’로 표시하지 않는다.
- 원격 삭제 전 미전송 기기의 존재·최종 백업·영향 범위를 안내하고 최종 확인을 받는다. 남은 기기의 캐시를 원격으로 완전히 삭제할 수 있다고 약속하지 않는다.
- 탈퇴 뒤 백업 잔존·법적 보관·폐기 시점은 개인정보/운영 정책을 작성할 때 확정한다. 아직 정하지 않은 삭제 기한을 약관처럼 고정하지 않는다.

## 5.6 이 단계에서 확정·보류하는 것

- 확정: 개인용/외부 서비스용 퍼블릭 클라우드 저장 가능한 구조가 필요하다.
- 설계 진행 기준: 로컬 전용을 유지하면서 사용자가 공간별로 온라인 연결.
- 추천/검토 중: 단일 리전·암호화 A·백업30일/수동10개·관리형 백엔드.
- 미선정: 공급자·실제 리전·요금·보관 용량·Auth/메일의 처리 국가·E2EE 최종 채택 여부.
