## 24.1 이번 단계의 결정 범위

23문서의 공개 한도 확인 이후, **클라우드 계정이 없어도 검증 가능한 동기화 핵심**을 첫 구현 단위로 분리한다. G0의 암호화·첫 플랫폼은 사용자 확정이며 나머지 구성은 표에 표시한 추천/미확정 상태로 둔다.

| 항목 | 권장 구성 | 상태/변경 영향 |
|---|---|---|
| 암호화 | TLS+서버 저장 암호화부터 | 사용자 확정(2026-11-08). 허가된 서버 본문 처리 가능, 실제 공급자 설정 검증 별도 |
| 첫 플랫폼 | Windows·macOS Desktop | 사용자 확정(2026-11-08). Web/Mobile은 같은 도메인 계약의 후속 어댑터 |
| 작업 기준 백엔드 | Supabase Auth/Postgres/private Storage·서버 명령 API | 최종 계정/조건 미확인. Neon 대안 유지 |
| 지역 | 서울 우선, 불가 시 도쿄/싱가포르 비교 | 아시아 범위만 사용자 확정. 정확한 리전은 미확정 |
| 전달 방식 | 활성 공간의 수동/5분 주기 | 추천. 즉시 알림은 후속이며 poll의 정합성 근거가 되지 않음 |
| 가입/복구 | 이메일 OTP, 아래 제한적 복구안 | 추천. 외부 SMTP/도메인·계정 복구 정책 미확정 |
| 비용 | 로컬 가상 데이터 시험부터, 초기 유료 자원0개 | 클라우드 무료량·메일/도메인 합산 비용·금액 상한은 별도 확인 |

### 계정 복구의 최소 운영안

1. 이메일에 접근 가능하면 OTP로 새 기기를 연결하고 안정된 accountId를 유지한다.
2. 이메일 변경은 인증 사업자가 지원하는 재인증·주소 검증을 통과한 경로만 제공한다. 기존 로그인 세션 하나가 있다는 사실만으로 분실한 이메일의 변경을 보장하지 않는다.
3. 이메일과 인증 수단을 모두 잃었을 때, 관리자가 문의 메일/공간 이름/로컬 사본만 보고 원격 공간 소유권을 넘기는 복구는 1차에서 제공하지 않는 안을 추천한다. 이 제한은 가입/도움말에서 설명한다.
4. 남아 있는 로컬 사본은 로컬로 계속 열고 내보낼 수 있게 한다. 새 계정으로 자료를 가져오려면 **새 공간을 생성하는 명시적 가져오기**로 처리한다. 이전 계정의 binding·pending op·소유권은 옮기지 않고, 기존 원격 공간을 복구했다고 표시하지 않는다.
5. 복구 코드/MFA·E2EE 복호 키 복구는 별도 설계 선택이다. 위 안으로 기존 원격 데이터 접근 복구나 자동 탈퇴/삭제를 약속하지 않는다.

## 24.4 미전송 편집을 지키는 로컬 상태

로컬 화면 데이터 하나에 서버 pull을 덮어쓰는 구현을 하지 않는다. 최소 다음 역할을 구분한다. 실제 테이블/필드 이름은 구현 계약에서 정한다.

- **서버 기준 사본:** 마지막으로 확인한 서버 payload/revision/checkpoint. 수신 순서에 따라 갱신한다.
- **편집 사본:** 사용자가 현재 보고 편집한 내용과 로컬 문서 revision. 저장 성공을 판단하는 대상이다.
- **편집 기준:** 해당 로컬 수정이 출발한 서버 revision/내용. 원격 변경과 비교할 근거로 보존한다.
- **전송 명령:** opId·기대 revision·payload/hash·의존 명령·상태. 최초 전송 시도 전에 영속화한다.
- **충돌 사본:** 공통 기준·내 수정·현재 서버 내용·비교한 revision. 해결 중 새 revision이 오면 다시 비교한다.

수신은 서버 기준 사본과 cursor를 원자적으로 갱신한다. 로컬 수정이 없으면 편집 사본에도 반영한다. 같은 aggregate에 pending/편집이 있으면 이를 보존하고 비교·충돌 상태를 갱신한다. 서로 다른 업무항목의 독립 수정은 합칠 수 있지만, 같은 노트/보드 JSON의 임의 필드 병합은 첫 단위에 포함하지 않는다. 수신 때문에 outbox를 다시 만드는 echo도 금지한다.

**자기 자신의 연속 편집:** 같은 aggregate는 첫 PoC에서 전송 중 명령1개로 제한한다. 아직 한 번도 전송하지 않은 대기 상태만 coalesce할 수 있다. 전송 시도한 opId의 payload/baseRevision/hash는 응답 유실 시에도 바꾸지 않는다. 추가 편집은 별도 대기로 보존한다. ack가 오면 해당 op만 완료하고, 그 op 이후의 편집은 남긴다. 새 명령을 만들 때는 최신 서버 상태와 기존 편집 기준을 비교하며, 다른 기기의 변경이 끼었으면 자기 수정이라고 자동 rebase하지 않는다.

ack의 수락 결과/서버 기준 갱신·해당 op 완료 표시는 한 로컬 batch로 기록한다. 중간 종료 후 같은 op를 다시 보내도 후속 편집이 지워지지 않아야 한다. ‘동기화됨’은 ack 하나를 받은 사실이 아니라 현재 scope의 미전송/미해결 변경이 없는 상태로 판단한다.

예: 서버 r10 → A가 문서 X 수정(op1, base10) → 응답 대기 중 X를 또 수정 → op1 ack r11. 화면에는 두 번째 수정이 남아야 하고, op1은 재전송해도 같은 결과여야 한다. 이후 서버가 그대로면 새 op2(base11)를 만든다. 중간에 B가 r12를 만들었다면 두 번째 수정을 보존한 채 비교가 필요하다.

## 24.5 명령과 동시성 단위

| 행위 | 검증 단위/처리 |
|---|---|
| 한 항목의 본문·완료/중요 변경 | 항목 ID+서버 revision. 다른 항목 수정과 불필요한 셀 전체 충돌을 만들지 않음 |
| 추가·삭제·순서/깊이·날짜 이동 | 영향받는 항목과 셀 membership/order의 기대 버전을 함께 검증. 이동은 받는/보내는 셀을 한 명령으로 처리 |
| 주간/업무 보드·업무 노트 | 문서 aggregate와 연결 관계를 하나의 명령으로 처리. 본문 수락 뒤 링크만 실패하는 부분 성공 금지 |
| 부모 범위 삭제와 자식 수정 | seq/depth의 삭제 범위·관련 버전 검사. 충돌하면 자식 편집을 복구 가능한 사본으로 남기고 자동 부활시키지 않음 |
| 복원 | restore operation ID·기대 generation·manifest 검증. 새 generation 공개와 기록을 원자화하고 재요청은 같은 결과 |

같은 셀의 다른 항목 본문 수정은 항목 단위 수렴을 검증한다. 순서 변경과 구조 변경은 별도 버전으로 보수적으로 충돌시킨다. 클라이언트가 보낸 전체 셀에서 빠졌다는 이유만으로 서버의 새 항목을 삭제하지 않는다. 실제 제품 전체 명령 목록/정렬 정책은 PoC 결과 후 확대한다.

커밋 순서 cursor는22문서의 공간별 직렬화 원칙을 따른다. 중복 op 동시 제출은 고유 제약/트랜잭션으로 한 번만 수락해야 한다. 요청 canonical hash는 타입/키 순서를 고정한 계약으로 계산하되 사용자 텍스트의 공백·개행·Unicode를 임의로 정규화하지 않는다. 인증 토큰·재시도 시각은 불변 명령 payload에 섞지 않는다.

서버 모형의 권한 거절은 실제 RLS/Storage 정책의 증거가 아니다. L01~L08 통과로 P01~P22 전체나 클라우드/실기 통과를 대신하지 않는다.13·15문서의 레지스터는 현재 모두 NOT_RUN이다.

## 24.7 성능·표시 판정 보완

서버 커밋 지연, 전송 스케줄 대기, 상대 기기 수신/적용 지연을 분리한다. 기본5분 polling에서 사용자의 변경이 항상5초 안에 상대 기기에 보인다고 요구하거나 약속할 수 없다. 첫 로컬 단위는 수렴/보존의 정합성이 통과 기준이며 실제 네트워크 성능 결과가 아니다.

- 수동: 사용자가 동기화 실행한 시점부터 측정한다.
- 주기: 설정한 주기까지의 대기와 실행 지연을 구분해 측정한다. 앱 sleep/백그라운드 중에는 고정 시간 보장을 하지 않는다.
- 즉시: 후속 실제 연결 시험에서13문서의 p95 5초 비교 목표를 적용한다. 현재 미제공/미측정이며 서비스 SLA가 아니다.

로컬 ‘저장됨’과 온라인 ‘전송 대기/동기화 중/충돌/동기화됨’을 구분한다. 로컬 저장 실패를 온라인 장애로 가리지 않고, 연결 실패 중에도 보존된 편집을 동기화 완료로 표시하지 않는다.

## 24.8 실행 전 검토와 이후 순서

첫 구현 단위의 검토 대상은 **확정된 암호화/플랫폼·나머지 권장 가정·W01~W05의 제한된 로컬 범위·가상 F0/F3·실험용 파일/증거 경로·L01~L08**이다. 기존 앱 전체 교체나 실제 클라우드 접근은 포함하지 않는다. 두 설계 선택을 반영했으며 로컬 PoC의 구현 범위 확정은 별도다.

클라우드 W06 이후에는 계정의 실제 Free 여유·서울/대체 리전·시험 프로젝트/정리 범위·외부 SMTP/도메인·예산을 확인한다. 키/비밀번호는 채팅·Git 문서로 수집하지 않는다. 로컬 PoC 결과로 계약을 수정하고 나서 실제 Auth/RLS/Postgres/Storage 시험을 연결한다.

## 24.9 첫 로컬 구현 묶음 — 최종 검토 대상

**상태: 설계 정리 완료·구현 미착수.** 사용자의 최초 요청은 신규 브랜치에서 ‘상세설계만 우선 논의’하는 범위다. 암호화/플랫폼 선택은 반영했으며, 아래 묶음의 구현으로 넘어가는 확인을 받는다. 추가 클라우드 결정이 남았다는 이유로 이 로컬 묶음의 설계를 계속 확대하지 않는다.

| 항목 | 이번 묶음에 고정할 내용 |

### 가상 데이터 기준선

아래는13문서 F0/F3의 첫 로컬 구현용 구체 크기다. 전체 V1 데이터 유형을 지원한다고 판단하는 기준이 아니다.

| 자료 | 고정할 내용 | 검증점 |
|---|---|---|
| F0 최소 원본 | 업무2·태그2·주차2(`2026-W44`, `2026-W45`)·항목8(상위6/하위2)·반복규칙1 및 발생 표본 | 완료/중요·날짜/주차·순서/깊이·반복 발생 키 유지 |
| F0 문서/자산 | 업무노트2·주간 보드2·업무 보드2·가상 이미지2 | 본문/블록·객체·연결선·링크·자산 소유자/hash |
| 링크 표본 | 주간 메모↔항목, 업무 보드↔항목, 자료함↔항목을 각1개 이상 | 연결 대상/공간 범위·본문과 링크의 원자성 |
| W2/C 범위 | 같은 주차/표시명·일부 겹치는 로컬 ID를 별도 공간/계정에 배치 | 이름/주차/로컬 ID가 같아도 혼입/권한 우회 없음 |
| F3 충돌 | 같은 F0 기준의 A/B 수정·삭제·제3 revision·구 generation pending | 기준/내 수정/서버 사본과 거절된 변경 복구 가능 |

가상 ID·시계·정렬·이미지 bytes를 seed로 고정하고 생성한 원본의 manifest/hash를 실행 전에 기록한다. V1 원본은 닫힌 가상 DB 파일로 동결한다. PoC는 직접 생성한 임시 디렉터리와 표시 파일이 있는 시험 DB만 열고, 실제 사용자 DB/기존 workspace 경로를 입력받는 기능은 만들지 않는다. 생성기가 지원하지 않는 레코드/포맷은 조용히 제외하지 않고 시험/전환을 중단해 기록한다.

반복은 고정 seed17/41/73을 사용한다. 중복/순서 역전이 의미 있는 사례는 정상 순서와 해당 장애 스케줄을 각각 실행한다. 동일 로그를 세 번 출력한 것을 반복 시험으로 세지 않으며, 하위 사례별 예정/실행/통과 건수를 보고한다.

## 24.10 증거와 완료 판정

첫 단위의 완료 조건은 다음을 모두 만족하는 것이다.

1. L01~L08의 필수 세부 경로가 계획된 로컬 환경에서 PASS이고 FAIL/BLOCKED/NOT_RUN이 남지 않는다. 일부를 구현하지 못하면 첫 단위 전체를 완료로 기록하지 않는다.
2. V1 가상 원본 hash 불변·항목/문서/자산 manifest 일치·교차 scope 혼입0·반쪽 batch0·중복 op 적용0·미전송 편집 유실0을 실제 기대/결과 diff로 확인한다.
3. L02/L04의 종료 증거에는 자식 프로세스 종료 지점·종료 상태·재시작 후 파일 DB 조회/무결성 확인을 포함한다. L03/L07은 응답 유실 전후 동일 op의 결과와 후속 편집/generation 보존을 확인한다.
4. 모형에 구현한 명령/포맷 목록과 미지원 목록을 보고한다. 서버 모형 통과를 실제 PostgreSQL 트랜잭션·RLS/인증/Storage·Windows/macOS 검증으로 표시하지 않는다.
5. 제품 경로/원본·공식 버전·기존 migration의 변경 여부와 재현 방법을 보고하고, 검토자가 같은 seed/실행 순서로 다시 실행할 수 있게 한다.

증거 manifest에는 `runId, codeCommit, fixtureHash, seed, case/subcase, runtime/OS, adapter, faultPoint, expected, actual, status, evidencePath`를 기록한다. 원시 DB/가상 이미지·상세 trace는 임시 실행 디렉터리에 보관하고, Git에는 가상 생성 규칙·기대값·요약/재현 보고서만 남기는 안으로 고정한다. 실패 기록은 후속 성공으로 삭제하지 않는다.

현재 L01~L08와 P01~P22는 모두 미실행이다. 구현 후 로컬 L사례 결과를 별도로 보고하고, P레지스터의 전체 환경 상태는 클라우드/실기 증거가 갖춰질 때까지 NOT_RUN으로 유지한다. 이번 문서 검증과 도구 가용성 확인은 PoC 통과 결과가 아니다.
