## 1. 순수 핵심

| 파일 | 내용 | 쓰는 곳 |
|---|---|---|
| `poc/v2-sync/hash-core.mjs` | 정준 JSON, 동기 SHA-256(순수 JS), base64 | 앱 엔진 |
| `poc/v2-assets/copy-core.mjs` | 원본 읽기 검사(판·구조·journal_mode·무결성·FK·삭제 잠금·칸반 쉬는 상태·문서 참조), 그림 base64 → 참조 + 바이트, manifest·`recordHash`·`blobHash` | `db18.mjs captureWorkspace`·`connected-copy.mjs`(Node) · 앱 엔진 |
| `poc/v2-migration/workspace-map-core.mjs` | DB18/19/20 → 온라인 봉투(계약 지문·제외 목록·폴더 경로 끊기·설정 투영) | `workspace-map.mjs`(Node) · 앱 엔진 |

- 의존성(해시·UUID·base64)은 넣어 준다 — Node는 `node:crypto`/`Buffer`, 앱은 `hash-core`/`crypto.randomUUID`.
- 형식 선언 `*.d.mts`를 옆에 두어 앱(TypeScript strict)이 그대로 가져온다.
- 행 정렬은 미리 계산한 해시로 한 번만(예전: 비교마다 해시 2번), 16진 문자열이라 바이트 비교 = 예전 `localeCompare` 순서(언어 설정과 무관).
- 기존 Node PoC 시험은 그대로(바뀌기 전과 같은 통과 수 — Docker가 필요한 41건은 이 환경에서 원래도 실패).

## 2. 앱 엔진

`prepareCopy(SQL, 사본 바이트, { workspaceId, sourceWorkspaceId })` → `{ header, pages, assets, assetBytes, mappingHash, sourceHash }`

- 기대 구조 = 제품 마이그레이션(`src/data/migrations/00*.sql`)만 적용한 빈 sql.js DB의 `sqlite_master` — 원본 구조가 정확히 같아야 한다(다르면 `SCHEMA_UNSUPPORTED`).
- 페이지: 1,000행씩. 서버 010은 **페이지 수 = 올림(기록/1000)** 을 요구해 크기로 더 나눌 수 없다 → 한 페이지가 약 1MB를 넘으면 `PAGE_TOO_LARGE`로 **보내기 전에 멈춘다**(6절 D-a).
- 보내기 전 한도: 기록 20,000·페이지 32·그림 2,000개·개당 10MB·합계 200MB(서버와 같음).
- 그림 바이트는 메모리에만(기록 파일·화면 상태에 넣지 않음). 사본 바이트는 바꾸지 않는다.

## 3. 실행기·통신

| 단계 | 호출 | 끊긴 뒤 |
|---|---|---|
| 기록 | `upload_begin` → `upload_status`(받은 페이지) → 빠진 `upload_page`만 → `start_upload` | 같은 작업 ID로 다시 부르면 빠진 페이지만 |
| 그림 | `observe` → 예약이면 `renew`(5분 연장) → 올리기(Rust가 SHA-256·크기 재확인) → `attest`(gateway가 저장소에서 다시 읽어 확인) | 확인된 그림은 건너뜀, 이미 올라간 것은 확인만 |
| 게시 | 모든 그림 다시 `attest`(서버는 **60초 안의 확인만** 인정) → `publication` → `prepare_publish` → `publish` | 게시 작업 번호를 기록해 같은 번호로 다시 |
| 취소 | `cancel`(게시 막기) → 그림마다 지우기 → `confirm-absent` → `finish_cancel` | 취소 작업 번호 기록, 지우기 확인은 약 100초까지 다시(4절) |

- 다른 사본(해시가 다름)으로 같은 작업을 이어 가려 하면 `MIGRATION_SOURCE_CHANGED`. 게시된 작업은 취소 불가, 취소한 작업은 다시 못 올림.
- 시작 전 취소 = 이 기기 기록만 지운다(서버에 남은 업로드 페이지는 서버 정리 몫 — 6절 D-d).
- Rust 명령(Preview만, `appProfile` 시험이 목록 고정): `migration_device`·`migration_command`(허용 명령만, 본문 1.1MB 한도)·`migration_put_asset`(IPC 원본 바이트)·`migration_cancel_asset`·`migration_journal_list/write/remove`. 주소는 개발 프로젝트 gateway 경로만, 리디렉션 따라가지 않음, 응답 1MB 한도.
- 오류 코드: 이관 경로 `{"error":"CODE"}`, 그림 경로 `{"error":{"code":"CODE"}}` 둘 다 읽는다(실서버에서 찾은 차이).

## 4. 실서버에서 찾은 것 — 지운 그림이 약 60초 더 읽힘

취소 시험에서 gateway의 그림 지우기가 계속 `DELETE_NOT_CONFIRMED`였다. 확인 결과 저장소에는 이미 없는데, gateway가 "없음"을 다시 읽어 확인하는 요청이 **약 60초 동안 캐시된 옛 본문**을 받았다(20초 간격 4번째에 통과). 이 세션에서 직접 지우고 읽으면 바로 없음 → gateway(Edge) 쪽 경로에서만 생기는 저장소 캐시로 본다.

- 지금: 앱이 2·5·10·20·30·30초 간격으로 다시 보낸다(약 100초). 할당량은 확인될 때까지 돌려주지 않으므로(보수적) 안전하다.
- 근본 수정 제안(D-c): gateway의 "없음 확인"을 캐시를 거치지 않는 조회(목록·정보 조회)로 → 개발 gateway 재배포 필요.
- 운영 전 확인: 지운 비공개 그림이 캐시에 남는 시간(접근은 gateway 서버 열쇠로만이라 사용자에게 노출되지 않음).

## 6. 결정이 필요한 것(서버 계약)

| | 문제 | 제안 |
|---|---|---|
| D-a | 서버 010이 페이지 수를 `올림(기록/1000)`으로 고정 → 긴 메모가 몰린 일지는 1,000행이 1MB를 넘어 **올릴 수 없다**(`PAGE_TOO_LARGE`) | 전진 SQL 013: 페이지 수 1~32 자유(기록 수 범위만 확인), 앱이 크기 기준으로 나눔 |
| D-b | 게시 직전 확인이 **60초 안**이어야 해 그림이 많으면(예: 200MB) 다시 확인(저장소에서 다시 읽기)을 60초 안에 못 끝낸다 | 013: 확인 시각 대신 "확인한 입출력 판 = 지금 판"과 진행 중 입출력 없음으로 판정(이미 검사 중), 또는 창을 30분으로 |
| D-c | 4절 캐시 — 취소가 약 1분 늦음 | gateway "없음 확인"을 캐시 없는 조회로 + 재배포 |
| D-d | 시작 전 취소 시 서버에 업로드 페이지가 남음 | 013: 오래된(예: 24시간) 시작 안 된 업로드 정리 또는 `upload_cancel` 명령 |

넷 다 **개발 서버 변경**(SQL 적용·gateway 재배포)이라 사용자 승인 뒤 진행한다. C-4 화면은 이 결정과 별개로 만들 수 있다(한도에 걸리면 화면이 이유를 알려 줌).

## 7. 한계·다음
