# 20. 신규 Supabase 계정·조건부 Keep Alive 기본 요구

2026-11-08 (KST) · 설계 전용. 신규 계정/프로젝트/DB에는 접속하거나 변경하지 않았다.

## 20.1 사용자 확정과 아직 미확정인 것

- 사용자가 Supabase 신규 계정을 만들었다고 알려 주었다. 기존 계정의 무료 프로젝트2개 소진을 이유로 Supabase를 배제하던 전제는 갱신한다.
- **Supabase를 채택하면 Keep Alive를 기본 포함**하도록 요청했다. 이전 woori-bldg의 방식이 참고 구현이다.
- 신규 계정 생성은 V2 프로젝트·리전·무료 잔여량·결제 조건의 검증 완료나 백엔드 최종 선택과 다르다. 현재 설계는 Supabase 통합 구성과 Neon 조합을 비용 비교할 수 있는 상태로 되돌린다.
- 실제 앱 구현/프로젝트 생성·SQL 적용·스케줄 등록은 아직 승인 범위에 포함하지 않는다.

## 20.2 기본 방식 — woori 사례 기반

근거: [woori-bldg 0012_keepalive.sql](https://github.com/chs2147/woori-bldg/blob/a8fdf4733987e77ddce359b4caf4d4642d8ebae5/supabase/migrations/0012_keepalive.sql).

| 항목 | 기본 설계 |
|---|---|
| 적용 대상 | 실제 연결한 Supabase 원격 프로젝트별 기본 활성. 로컬 환경은 휴면 방지 목적의 실행 불필요 |
| 실행 | pg_cron 하루1회, 예시03:00 UTC=12:00 KST. 정확한 시각은 운영 설정으로 고정 |
| 기록 | 전용 테이블의 고정1행에 마지막 성공 시각 upsert |
| 격리 | 업무/이미지/사용자 기록과 분리. RLS 활성·일반 anon/authenticated 접근 차단 |
| 중복 방지 | migration 재적용/배포 시 같은 job이 누적되지 않도록 이름/ID 확인·등록 정합성 유지 |
| 상태 | job 등록 여부·마지막 성공·실패 횟수·실제 프로젝트 연결 상태를 구분 |
| 사용량 | 하루1회면 월 약28~31회 실행/프로젝트. 실행 로그·다른 서비스 사용량은 별도 |

테이블은1행이어도 cron 실행 로그는 늘 수 있다. 해당 job의 로그 보관과 정리를 운영 정책에 포함하고 다른 job/업무 로그를 임의로 삭제하지 않는다. DB 내부 실행에 관리자 키를 외부 배포할 필요는 없다.

## 20.3 보장 범위와 보완 검증

**DB 내부 cron이 동작한다는 것과 플랫폼의 휴면 판정에서 활동으로 인정된다는 것은 같은 보장이 아니다.** woori에 적용한 코드·기록은 확인했지만 현재 Supabase 정책에서 이 방식의 영구적인 휴면 방지 효과를 공식 검증한 것은 아니다.

- 실제 선택 플랜의 pause 기준·cron 가용성/영향·사용량을 확인한다. 업무 활동이 없는 기간의 프로젝트 상태와 heartbeat 성공 기록을 관찰한다.
- 프로젝트가 이미 pause되면 그 안의 cron도 재개 수단이 되지 못할 수 있다. 자동 재개 API를 임의 호출하는 기능을 전제로 두지 않는다.
- 보완이 필요하면 별도 외부 스케줄에서 하루1회 제한된 상태/DB 요청을 하는 안을 비교한다. 단순 웹 정적 페이지200 응답을 DB 정상 증거로 사용하지 않는다.
- 외부 점검이 필요해도 service-role/DB 관리자 키를 공개 저장소·브라우저에 넣지 않는다. 제한된 인증·쿼리·재시도·요청량으로 설계하고 실제 과금/이용 조건을 확인한다.
- DB 접근이 필요한 상태 확인을 매초/매분 반복하지 않는다. Keep Alive와 기기간 동기화 polling은 목적/주기가 다른 작업이다.

화면/도움말은 ‘Keep Alive 설정됨·마지막 실행’과 ‘현재 온라인 연결 상태’를 따로 표시한다. ‘휴면이 절대 발생하지 않음’·‘무중단 보장’이라고 안내하지 않는다.

## 20.4 휴면·연결 실패 시 동작

- 로컬 저장/편집을 계속하고 outbox를 보존한다. 온라인 저장까지 완료된 것으로 표시하지 않는다.
- 원인이 확인된 경우 ‘프로젝트 일시중지/재개 필요’, 일반 timeout이면 ‘연결 확인 필요’로 구분한다. 모든 실패를 휴면이라고 단정하지 않는다.
- 관리자는 콘솔에서 상태/재개·플랜 제한을 확인한다. 앱은 재연결 후 기존 cursor/generation을 검증해 이어간다.
- Keep Alive는 백업을 대체하지 않는다. 프로젝트 재개 실패/제한·실수에 대비한 로컬 안전 사본과 검증된 복구본은 유지한다.

## 20.5 제공자별 차이 유지

Supabase 선택 시: 이 문서의 Keep Alive를 기본 요구로 포함하고 동작/휴면 정책을 검증한다.

Neon 선택 시: 기존 사례에 따라 scale-to-zero를 허용하고 인위적인 keep-alive는 기본 적용하지 않는다. 반복 쿼리가 컴퓨팅 예산을 소모할 수 있으므로 제공자별 정책을 분리한다.

따라서 `keepAliveEnabled` 같은 설정을 모든 백엔드에서 공통으로 켜는 구조는 채택하지 않는다. 선택한 제공자의 관리 기능으로 한정하고, 최종 공급자/플랜이 정해질 때 실제 동작을 잠근다.
