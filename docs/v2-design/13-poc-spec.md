# 13. PoC 검증 명세·증거 수집 계획

2026-11-08 (KST) · 설계 전용 · **미실행**

**최신 비용 원칙:** [16문서](16-low-cost-review.md). 주기/수동 우선·즉시는 조건부다.22개 시나리오는 유지하고, 제공하지 않는 선택 모드의 실행은 BLOCKED/범위 보류로 명시하며 PASS로 대체하지 않는다.

## 13.1 목적과 실행 경계

가상 데이터로 ‘V1 원본을 보존하면서 두 기기의 로컬 우선 변경을 손실 없이 수렴시킬 수 있는지’를 증명한다. 현재 앱이나 실제 업무 DB를 시험 대상으로 사용하지 않는다. 코드 작성/패키지 설치/클라우드 생성·메일 발송·결제/자료 업로드는 이 문서 작성에 포함하지 않는다.

실행 승인 시 테스트 계정·아시아 내 테스트 리전·과금 상한·시험 데이터·로그/보관·정리 담당을 고정한다. 운영 서비스와 별도 환경을 쓰고, 테스트 자원 정리는 승인된 범위와 이름에 한정한다.

## 13.2 시험 환경

- A/B 두 기기: 같은 개인 계정·같은 온라인 공간, 서로 다른 device/session. 초기에는 두 독립 프로세스, 후반에는 Windows/macOS 실기로 확인.
- C 다른 계정: 같은 이름의 공간·추측한 객체 ID를 사용해 계정 간 격리 검사.
- 동일 계정의 별도 공간 W2: 같은 주차 키와 유사 업무명을 사용해 공간 혼입 검사.
- 오류 주입: 네트워크 차단/지연·응답 유실·중복·서버 재시작·앱 강제 종료·토큰 만료·용량 초과·이전 generation 요청.
- 시간대: Asia/Seoul과 별도 지역 타임존. 클라이언트 시계는 서버보다 앞/뒤로 설정한 사례를 포함한다. 날짜/주차와 표시 timestamp를 구분한다.

## 13.3 fixture와 판정 자료

| fixture | 제안 크기 | 검증 대상 |
|---|---|---|
| F0 최소 | 업무2·부모/자식 항목·완료/중요·태그·주차2개 | 키/정렬·부모/자식·반복·주차 경계 |
| F1 대표 | 업무10·항목1,000·노트20·주간 보드4·업무 보드10·이미지20 | 관계/JSON/서식·노트/자료 링크·계층 목록·표 |
| F2 용량 | 항목100,000·이미지200개×256KiB(50MiB), 고정 seed | chunk/재개·조회/GC·동기화 시간/메모리 |
| F3 충돌 | 공통 조상·기기 A/B 수정·삭제·제3의 새 revision | 기대되는 사본과 거절/수락 상태 |

fixture는 구현 단계에서 생성·승인한다. 이미지 수/크기뿐 아니라 문서·참조·metadata 크기도 기록한다. F2를100명 실사용 비용/동시 접속 시험으로 간주하지 않는다.

각 fixture manifest에는 entity별 ID/버전/정규화한 payload hash, 자산 실제 byte hash·크기/mime, 참조·부모/자식·문서 수를 기록한다. 단순 총 개수 일치만으로 내용 유실/중복/원본 변경을 통과시키지 않는다.

## 13.4 기능·장애 시나리오

|---|---|---|---|
| P01 | V1 사본 생성·전환 후 원본 비교 | V1 원본 byte hash 유지, V2 참조/자산 검증 | 필수 |
| P02 | 로컬 데이터 기록과 outbox 기록 사이 종료 | 둘 다 커밋 또는 둘 다 취소. 저장만 되고 전송 큐가 빠지는 상태 없음 | 필수 |

| P07 | 부모 삭제와 자식 수정/생성 | 고아 레코드/참조 금지, 수정 사본 복구 가능 | 필수 |

| P14 | 전체 복원 후 구 generation의 pending op 전송 | 재조정 전 자동 수락0, 기존 사본/변경 보존 | 필수 |

## 13.5 시간·용량·입력 성능 측정

- 로컬 편집/저장 latency, outbox 누적/해소, 서버 커밋·다른 기기 수신 지연, 최초 upload/download·메모리, 명령당 요청/DB op·자산/egress를 별도 계측한다.
- 권장 실험값: 즉시750ms debounce·최대5초 묶음, 활성 공간의5분 보완 pull 후보, 주기5분. ‘최대5초’는 네트워크 전송 시도 목표이며 서버 확정시간 보장이 아니다.
- F1의 **즉시 모드** 일반 연결 조건에서 상대 기기 반영 p95 5초 이내를 초기 비교 목표로 두되 네트워크/하드웨어/표본을 함께 기록한다. 기본5분 주기 모드에는 이 목표를 적용하지 않고 스케줄 대기와 실제 전송/적용 지연을 나눈다([24문서](24-local-poc-review-package.md)). 실패하면 보장 문구를 바꾸거나 원인을 개선하고 재측정한다.
- 입력 성능은 같은 기기·같은 fixture의 현재 로컬 앱 baseline과 비교한다. 동기화 부하가 편집을 막지 않는지 p50/p95와 긴 작업을 본다. 최종 기준은 첫 baseline 측정 후 확정한다.
- 동시 연결/대량 부하는 별도 시험이다.100명 용량 가정이나 두 기기 성공만으로100명 동시 사용 통과라고 하지 않는다.

## 13.6 증거·결과표

각 실행은 commit·앱/DB/protocol/format 버전, fixture hash, OS·CPU/메모리·locale/time zone, API/DB 리전/플랜, 네트워크 조건, 시작/종료·결과·실패 opId·재시도·복구 방법을 기록한다. 토큰/OTP·이메일 원문·실제 사용자 내용은 기록하지 않는다.

결과 상태: `NOT_RUN / BLOCKED / PASS / FAIL`. 시험 ID별 증거 파일(검증 diff·렌더링·승인된 로그·화면)과 재현 방법을 연결한다. 테스트 서비스에 접근하지 못한 항목은 PASS가 아니다.

## 13.7 종료 기준과 다음 산출물

1. 필수 P01~P22를 합의된 환경에서 통과하고 실패/차단 항목을 남기지 않는다. 장애 시나리오는 반복 횟수와 결정적 재현을 기록한다.
2. 실제 복원과 원본 보존·계정/공간 격리의 증거를 확인한다. 서비스의 리전·세션 회수·백업 한도는 실제 설정/계약으로 검증한다.
3. 성능/비용 측정치를 바탕으로 공급자·저장/보관·동기화 기본값과 범위 추정을 재검토한다.
4. 미충족 조건은 기능 축소/추가 설계/대안 제공자로 조정하고, 고객용 MVP 출시는 별도로 승인한다.

현재 P01~P22는 모두 NOT_RUN이다. 다음 단계는 이 명세와 MVP 범위를 검토해 G0의 가정을 잠그는 것이며, 자동으로 PoC 코드 작성/서비스 배포로 넘어가지 않는다.
