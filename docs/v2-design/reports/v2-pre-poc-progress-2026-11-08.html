두 개편 축의 설계 성과

03 / DESIGN OUTPUTS
다국어 설계

하나의 언어 계약, 모든 고객 접점

2,680소스 내 번역 후보 발견 건수
15 / 19가이드 장면 / 스크린샷 조사
  • 한국어·영어 리소스 묶음, 의미 기반 키·치환 인자·공통 용어집의 계약을 작성했습니다.
  • 앱·네이티브 안내·내보내기·사이트·현재 가이드의 언어별 배포 관문을 제안했습니다.
  • 사용자 작성 내용과 업무 날짜는 번역·언어 전환으로 바꾸지 않는 원칙을 설계했습니다.

2,680건은 AST 조사 후보이며 확정 번역 키 수가 아닙니다. 전체 번역·리소스 구현은 미착수입니다.

온라인 동기화 설계

로컬 편집을 유지하며 변경분 전달

  • 로컬 SQLite와 서버 PostgreSQL이 공통 데이터 계약을 사용하고 실행 저장소는 분리하는 안을 구체화했습니다.
  • 기존 DB는 원본 보존 후 사본 전환, 메모 이미지·링크는 함께 검증하는 흐름을 작성했습니다.
  • 중복 전송·수신 순서·동시 수정·삭제·전체 복원 시의 처리 계약을 정리했습니다.
  • 서버 기준 사본과 미전송 편집을 나눠 수신 데이터가 사용자의 수정을 덮어쓰지 않도록 설계했습니다.

‘로컬 전용 / 온라인 백업 / 증분 동기화’는 별도 모드로 제안합니다. 백업과 다기기 동기화는 같은 기능으로 취급하지 않습니다.

현재 활성 기능 249개를 플랫폼별 검토 후보로 정리했습니다. 개별 기능의 V2 지원·출시를 검증한 목록은 아닙니다.

무료 운영 가능성을 검토한 결과

04 / BACKEND & COST

Supabase 통합 구성을 현재 상세 설계의 작업 기준으로 두고 Neon을 대안으로 유지합니다. 최종 제공자 선정과 실제 계정 조건 확인은 남아 있습니다.

공식 공개 소스의 Free 기준

DB · 프로젝트별500 MB
파일 저장소1 GB
월 일반 전송량5 GB
월 함수 호출50만 회

공식 소스 고정 커밋 기준입니다. DB 크기를 제외한 포함량은 원칙적으로 조직 합산이며 실제 계정 잔여량은 미확인입니다. cached egress는 별도 항목입니다.

실측이 아닌 용량 가정

5명으로 시작하면 용량상 가능성

5명 × 공간 1개 × 원본 25MiB
현재 데이터 1벌 + 원격 보존본 3개

평상시백업 교체 중 추가 공간
평상시 500MiB교체 중 625MiB

막대 기준은 1GB = 10억 bytes입니다. DB·썸네일·충돌 사본·다른 프로젝트 사용량은 별도입니다. 10명 × 50MiB 모델은 보존본 포함 2,000MiB로 무료 1GB를 초과합니다.

무료 운영의 추가 확인점: 외부 사용자 인증 메일에는 별도 SMTP가 필요합니다. 기본 메일러는 팀 주소·시간당 2통의 시험용 조건이므로 메일·도메인까지 합친 총비용 0원을 확정하지 않았습니다.

Keep Alive: Supabase 채택 시 하루 1회 기본 적용안입니다. DB 내부 cron이 휴면 판정에 인정되는지는 미검증이며, 이미 중지된 프로젝트를 재개하는 수단도 아닙니다.

비용 판단에 반영한 실제 프로젝트 사례
  • my-money-note: Neon의 연결·절전·분기 운영과 파일 최적화를 참고했습니다. 과거 무료 한도 상수·공개 이미지 URL·고정 사용자 인증은 V2에 그대로 적용하지 않습니다.
  • woori-bldg: Supabase 운영/개발 분리와 Keep Alive 코드를 분석했습니다. 관리형 DB branch도 과금될 수 있어, 무료 우선 개발은 로컬 환경을 권장합니다.
  • 두 저장소는 읽기 전용으로 분석했습니다. 기존 DB·프로젝트를 통합하거나 삭제하지 않았습니다.

다음 단계: 로컬 PoC

05 / PROPOSED VERIFICATION
범위·완료 기준 정리구현 미착수

가상 데이터와 두 기기로 데이터 보존부터 확인

가상 업무·노트·보드와 기기 A/B를 사용합니다. 별도 계정·공간 모형도 포함하며, 실제 업무 DB·클라우드·메일 발송 없이 로컬 파일과 프로세스로 검증하는 범위입니다.

L01기존 원본 보존과 사본 전환
L02저장 도중 종료해도 데이터·전송 대기 일치
L03응답 유실·중복 전송·연속 편집 보존
L04수신 적용 중 종료와 재시작
L05동일 문서 충돌과 새 수정 재비교
L06상위/하위 삭제와 날짜 이동의 동시 수정
L07복원 재요청·이전 세대 변경 차단
L08계정·공간 전환 뒤 지연 응답 혼입 방지

완료 기준: 필수 세부 경로를 통과하고 원본 hash·내용/참조 비교·실제 파일 DB 재시작 증거를 남깁니다. 데이터 유실·중복 적용·계정/공간 혼입을 확인합니다.

현재 실행 상태: 로컬 8개 사례와 전체 검증 시나리오 22개 모두 미실행입니다. Node24.22.1의 파일 SQLite 모듈 존재 확인만 했으며, PoC 통과 결과는 없습니다.

권장 진행 순서

  1. 첫 로컬 범위 검토·착수 확인정리한 8개 사례와 가상 자료·완료 기준을 검토합니다.
  2. 로컬 PoC 구현·검증실패·재현 증거를 보고하고 결과에 따라 계약을 보완합니다.
  3. 클라우드 조건 확정 후 실제 검증계정·리전·메일·예산 확인 뒤 인증/권한·DB·파일 저장을 시험합니다.

남은 결정과 확인

06 / OPEN ITEMS

클라우드 시험 전에 확인할 것

  • 최종 백엔드·실제 계정 플랜신규 계정 Free 여유, quota·초과 처리, 시험 환경 범위
  • 정확한 아시아 리전서울 우선 검토, 도쿄·싱가포르 대안 · 실제 선택 가능 상태 확인
  • SMTP·도메인·월 예산 상한외부 인증 메일 전달·발송 제한과 고정/변동 비용 합산

제품 정책으로 확정할 것

  • 계정 복구와 인증 방식이메일 OTP·분실 시 제한적 복구는 추천안이며 아직 미확정
  • 전송·보관·용량 기본값수동/5분 주기 우선, 원격 보존본 총 3개는 설계 제안
  • 최종 범위·일정·출시 관문로컬 결과와 실제 클라우드·Windows/macOS 검증 후 판단

위 클라우드 조건은 첫 로컬 모형 검증과 분리했습니다. 다국어 기술 작업의 기존 초안 추정은 32~58인일이며 번역·언어/법률 검수·신규 온라인 UI는 별도입니다. 확정 일정이나 전체 V2 공수는 아닙니다.
