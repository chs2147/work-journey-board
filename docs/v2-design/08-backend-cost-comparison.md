# 8. 백엔드 후보·용량·비용 비교 초안

2026-11-08 (KST). **제품 구성 비교이며 현재 가격표/제공 리전을 실시간 조회한 견적이 아니다.** 사업자별 공식 견적과 제공 조건은 아래 확인표를 채워야 확정할 수 있다. 서비스 가입·결제·프로젝트 생성은 하지 않았다.

사용자 추가 전제: **소규모 시작, 초기 아시아 리전**. 아래100명 모델은 비용 비교용 가정이며 확정 사용자 수/가입 한도가 아니다.

**최신 우선 기준:** [16 저비용 재검토](16-low-cost-review.md). AWS 직접 구성은 제외하며5명 소규모 시험을 비용 검증 기준으로 한다. 아래100/1,000/10,000명 표는 확장 민감도 자료다.

**후속 제약:** Supabase 신규 무료 프로젝트를 가정하지 않는다. [17 Neon 검토](17-neon-option.md)를 후보 순위/역할 분리의 최신 기준으로 적용한다.

## 8.1 후보 구성

| 안 | 구성 후보 | 현재 앱과의 적합성 | 주의·추가 작업 | 판단 |
|---|---|---|---|---|
| **A. Neon 중심 조합** | Neon PostgreSQL + 검증된 Auth/API/blob 후보 | SQL 관계·명령 계약 유지, Supabase 새 무료 프로젝트 불필요 | 연산/휴면·Auth·객체 저장·API 합산 비용·리전/정합성 확인 | **우선 비교 추천** |
| B. Supabase 최소 유료 구성 | Auth/PostgreSQL/Storage + Sync API | 구성 수를 줄일 수 있음 | 사용자 무료 프로젝트 여유 없음. 실제 추가 프로젝트 비용 확인 | 유료 총비용 비교 후보 |
| C. Firebase 중심 | Auth + Firestore + Cloud Storage + Functions/Cloud Run | 웹/모바일 SDK·알림 활용이 쉬운 편 | 기존 SQL 관계·정합성 단위를 문서 모델로 다시 매핑. SDK 오프라인 기능이 기존 SQLite와 자동 연동되는 것은 아님. 읽기/쓰기/리스너 비용 측정 필요 | 초기 SQL 모델 재사용 관점에서는 우선순위 낮음 |

공통: 서버가 업무 명령·공간 권한·baseRevision·generation을 검증하고 데이터/로그를 원자적으로 커밋해야 한다. 클라이언트가 공급자 DB를 직접 무제한 수정하는 방식은 채택하지 않는다. 핵심 계약을 `contracts/sync-core`에 두고 인증·blob·알림 제공자는 어댑터로 분리한다.

A를 검증 기준으로 쓰되 사업자를 확정한 것은 아니다. 특히 서울 등 희망 리전의 DB·Auth·Storage·백업이 요구를 모두 충족하는지 확인 전에는 ‘한국 내 전용 저장’으로 약속하지 않는다.

## 8.2 견적용 세 가지 부하 모델

아래는 사용자 수가 미확정인 상태에서 비교하기 위한 **계산 가정**이다. 실제 고객 예측·요금제 약속이 아니다. 활성 사용자당 공간2개, 공간당 원본100MiB, 하루 변경100건, 월22일 사용, 월 인증 메일4통, 동시 활성10%, 활성 사용자당 연결 기기2개를 동일하게 놓는다.

| 월 활성 사용자 | live 원본(GiB) | 월 변경 op | 인증 메일/월 | 동시 연결 수(가정) | 30개 전체 백업 단순복제(GiB) |
|---:|---:|---:|---:|---:|---:|
| 100 | 19.53 | 220,000 | 400 | 20 | 585.94 |
| 1,000 | 195.31 | 2,200,000 | 4,000 | 200 | 5,859.38 |
| 10,000 | 1,953.12 | 22,000,000 | 40,000 | 2,000 | 58,593.75 |

`GiB = 사용자×2×100/1024`.변경 op는 HTTP 요청/DB 쿼리 수가 아니다. 묶음/재시도/정합성 검사·change log 작성으로 과금 단위가 달라진다. 위 저장량에는 구조화 DB·로그·섬네일·업로드 staging·추가 수동 보존본이 빠져 있다. 최종 비용은 더 커질 수 있다.

전체 백업 단순복제 열은 비효율적인 구현의 용량 영향을 보여 주는 비교값이다. 실제 추천은 불변 blob 재사용+시점 manifest이지만 삭제된 과거 자산과 change log는 보관하므로 ‘백업 비용0’으로 산정하지 않는다.

## 8.3 총비용 산식과 누락 방지

월 총비용 = 고정 플랜 + Auth/인증 + DB 연산/저장/PITR + Sync API/worker + 실시간 연결/메시지 + 객체 live/보존본 + 다운로드 egress + 메일 + 모니터링 + 운영/지원 인력.

| 비용 축 | 견적에 넣을 입력 | PoC에서 측정할 값 |
|---|---|---|
| DB | 레코드·문서 크기·변경 이력/멱등 키 보관·인덱스 | 명령당 쿼리·커밋 지연·동시 연결·vacuum/정리 |
| API | op 묶음 크기·재전송·검증 | 요청당 CPU/메모리·timeout·유휴/상시 실행 |
| 실시간 | 활성 연결·수신자 수·재접속 | 알림/heartbeat/pull 빈도·증폭률 |
| 파일 | 원본·썸네일·보존 자산·staging | 실제 압축률·수정/삭제율·GC 지연 |
| 다운로드 | 새 기기·재동기화·복원·이미지 조회 | 캐시 적중률·장치당 초기 다운로드 크기 |
| 메일/Auth | MAU·인증 횟수·복구/보안 알림·불필요 요청 | 차단률·전달률·국가별 경로·공급자 한도 |
| 운영 | 장애 대응·복구 훈련·취약점/키 갱신 | 월 운영 시간·복원 소요·실제 보존 비용 |

소규모에서는 고정 DB/백업/메일 플랜이, 이미지 중심 사용자에서는 저장·egress가 더 클 수 있다. ‘무료로 가능한가’만으로 업체를 고르지 않고 무료 가능 범위와 개인 예산 내 최소 유료 구성으로 비교한다. 환율·부가세·지원 플랜은 견적 표시에서 구분한다.

## 8.5 추천 PoC와 선택 관문

1. A를 기준으로 가상 공간1개/기기2개에 대한 명령·revision·outbox·실제 이미지 전송 계약을 설계한다. 이는 실행 승인 전의 검증 계획이다.
2. 계정 전환·기기 회수·메일 전달·지정 리전·서명 URL·PDF/이미지 원본 저장 및 복원 가능성을 확인한다.
3. Neon 조합이 무료/개인 예산·리전·정합성 조건을 충족하지 못하면 범위/용량 또는 다른 저비용 후보를 재검토한다. AWS 직접 구성으로 자동 전환하지 않는다.
4. 선택 기준은 데이터/복구 조건 충족 → 정합성 → 운영 가능성 → 정상 운영 비용 → 이식성 순서다. 언어/도메인 코드를 공급자 SDK에 종속시키지 않는다.

다음 결정: 예상 월 사용자 규모와 공간당 이미지 용량, 첫 리전, 암호화 A/B, A 우선 PoC 여부. 어느 것도 실제 유료 자원 생성의 승인을 대신하지 않는다.

## 8.6 소규모·아시아 출발 구성

- 아시아 단일 primary region의 관리형 PostgreSQL/Auth/Storage와 단일 배포 단위의 Sync API를 우선 비교한다. 대규모 다중 리전·마이크로서비스·Kubernetes·별도 메시지 플랫폼을 초기 필수 구성으로 두지 않는다.
- 환경은 개발/운영을 분리하고 백업/복원은 초기부터 검증한다. 무료 플랜의 보존/운영 제한을 확인하지 않은 채 실사용 자료를 맡기지 않는다. API 권한/멱등성/충돌 검사는 소규모여도 생략하지 않는다.
- 아시아 범위는 사용자 확정이나 특정 국가/도시·모든 공급자의 Auth/메일/로그 처리 국가까지 확정한 것은 아니다. 본문/이미지·보존본·운영 로그는 아시아 저장을 목표로 검증하고, 인증/메일의 처리 경로는 별도로 확인해 서비스 설명에 명시한다. 전 세계 메일 배달 경로까지 아시아에 한정된다고 약속하지 않는다.
- 최초 비용 검증은16문서의5명 시험 가정을 기준으로 사용하고100명 이상은 확장 민감도로 남긴다. 실제 인원/이미지 용량·월 예산은 아직 정해지지 않았다.
