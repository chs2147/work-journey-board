# 46. 기존 로컬 모델 보호·V2 이미지 저장 효율 설계

2026-11-09 UTC · v2-design · 요구사항 기반 상세 설계 보완. **설계이며 제품/DB/이미지 처리 코드를 변경하지 않았다.** 기존 단계의 시험 통과로 아래 요구가 구현됐다고 간주하지 않는다.

## 고정 요구와 적용 범위

사용자 요구: V2 출시 후에도 기존 로컬 모델에 영향이 없어야 한다. V2 이미지는 DB에 본문을 직접 넣지 않고 중복 실물을 저장하지 않으며, 읽기 좋은 해상도/용량을 기준으로 최적화한다.

- 기존 V1 로컬판과 기존 DB/백업/설정/네트워크 규칙은 유지한다. 기존 SQLite 이미지/base64를 일괄 추출하거나 압축해 원본을 바꾸지 않는다.
- V2의 **로컬 전용 공간**도 기존 로컬 저장 계약을 유지한다. 계정/온라인 접속 없이 작성·검색·보드·내보내기·백업/복원이 가능해야 한다.
- 새로운 **V2 온라인 연결 공간**은 V1 원본에서 복사·검증한 별도 공간/저장 형식이다. 이미지 파일+metadata DB를 사용하는 예외는 이 새 형식에만 적용한다. 과거 로컬 모델의 단일 DB 보관 원칙을 소급 변경하지 않는다.
- 공통 도메인은 재사용하되 LocalLegacyRepository와 V2ConnectedRepository/AssetStore를 분리한다. 현재 제품에 이 인터페이스가 이미 구현됐다는 뜻은 아니다. 같은 원본 DB를 두 저장 어댑터로 번갈아 열지 않는다.

| 오프라인 | 로컬 전용 제품/프로필에 온라인 SDK 초기화·인증 복원·주기 네트워크·cloud env 필수값 없음. 기존 승인된 판 확인/링크 OS 열기 예외는 유지. 온라인 기능은 명시적 공간 연결 후 시작 |
| 온라인판 로컬 공간 | 로그인한 온라인판에는 계정 관리 통신이 있을 수 있음. 해당 로컬 공간의 본문/이미지/경로는 전송하지 않음. 이를 완전 통신0 제품과 혼동하지 않음 |
| 전환/되돌리기 | V1→V2 사본 변환 후 row/참조/자산 hash·첨부 복구 검증 뒤 활성화. 실패 시 V1 계속 사용. V2가 새 기록을 썼어도 V1 원본에 역동기화/덮어쓰기하지 않음 |
| 오프라인 자산 | 온라인 공간도 신규/미전송·충돌·로컬 보존 대상의 실물은 기기에 유지. 클라우드 장애/로그아웃/한도 초과가 기존 로컬 자료 읽기·편집·내보내기를 막지 않음 |
| 연결 해제 | 완전한 로컬 독립 사본을 원하는 경우 모든 참조 자산을 검증·확보한 뒤 분리. 누락 자산이 있으면 온라인 완전 해제/오프라인 준비 완료라고 표시하지 않고 재시도 또는 명시적 불완전 사본 안내 |
| 공유 코드 | 새 이미지/자산 처리·환경 선택을 온라인 어댑터에 한정. 공통 변경이 필요하면 V1 fixture/네트워크/복원 회귀 검증 후 별도 릴리스 판단 |

## V2 온라인 이미지 저장 구조

```text
문서/보드 DB: logicalAssetId → asset_reference → blob metadata
로컬 V2: workspace/assets/<opaqueBlobId>  (실물 binary, DB 밖)
클라우드: private bucket / workspaceId / opaqueBlobId / variantId
캐시: 축소 표시본, 삭제 가능 조건을 만족한 재생성 자료만
```

PostgreSQL/온라인 SQLite에는 ID·소유 workspace·hash·실물 byte수·MIME·픽셀 크기·처리 policyVersion·variant·상태·참조만 둔다. **base64/data URL/bytea 이미지 본문을 문서 JSON·outbox·change log·스냅샷 DB에 넣지 않는다.** 붙여넣기/가져오기 단계의 일시적 base64는 binary로 디코딩한 뒤 저장 경계에서 차단한다. V1 복사본 변환 시 추출은 V2 staging에서만 수행한다.

파일과 SQLite는 한 트랜잭션이 아니므로 임시 파일 기록→hash/길이 확인→flush/원자적 rename→DB 참조/outbox batch 순서와 durable import journal을 둔다. 파일 기록 완료 전 문서 참조를 확정하지 않는다. 종료 시 남은 stage 파일·DB 미참조 실물은 재개/GC 절차로 분류하고 미전송 자료를 임의 삭제하지 않는다. 서버도 실물 검증/ready 확정 후 문서 revision을 공개한다.

V2 온라인 공간의 백업은 SQLite 단독 파일이 아니라 **metadata snapshot + 참조 자산 manifest + 필요한 binary**를 담는 내보내기 패키지다. DB만 복사한 파일을 완전 백업으로 표시하지 않는다. 순수 로컬 기존 .db 백업 계약은 유지한다. 연결 해제 시 기존 로컬 DB 형식으로 복원할 경우 별도 내보내기 변환/검증을 통해 이미지를 다시 포함할 수 있다. 이는 호환성 사본이며 원본 V1 파일을 수정하는 작업이 아니다.

## 물리 중복 제거와 독립 객체의 양립

- 범위는 **동일 workspace 내부**다. dev/prod·다른 workspace/계정 간 실물 공유/전역 해시 조회는 하지 않는다. 다른 공간 복제는 새 공간 소유 자산으로 이관한다.
- logicalAssetId/객체/소유자 참조는 기존 복제 의미대로 별개다. 동일 최종 저장 bytes의 SHA-256/크기 검증으로 동일 workspace의 immutable blob 실물만 공유한다. 이미지 편집은 새 blob을 만들고 해당 참조만 교체한다(Copy-on-write).
- `blob(workspace_id, blob_id, stored_sha256, bytes, mime, width, height, state, policy_version)`에 workspace+stored_sha256 유일성을 두고, 별도 asset_reference/variant 관계를 둔다. 공유를 위한 active/pending 상태 전이와 재시도/고아 복구를 설계한다.
- 동시에 같은 이미지를 넣어도 서버의 unique 예약/원자적 quota/확정으로 실물1개만 ready가 되게 한다. 클라이언트 해시나 '존재함' 응답만으로 업로드 검증/소유권을 인정하지 않는다. 권한 없는 해시 존재 탐색을 허용하지 않는다.
- 중복 제거 보장은 **최종 binary가 동일할 때**다. 같은 그림이라도 코덱/품질/메타데이터가 다르면 다를 수 있다. perceptual hash로 비슷한 사진을 자동 병합하지 않는다. 같은 원본+처리 recipe를 재사용할 로컬 인덱스와 처리 버전을 두되 다른 장치의 bytes 동일성을 가정하지 않는다.
- 논리 복제마다 원본/썸네일 실물을 다시 올리지 않는다. 필요 variant도 기존 실물이 있으면 재사용한다. 물리 저장 quota와 참조 수/작업량 제한을 분리해 중복 참조 무제한 남용을 막는다.

## 해상도·압축 정책 초안

다음 수치는 **V2 온라인 전용 검증 시작값**이며 사용자 화질 검토·Windows/macOS 렌더링/성능 시험 후 확정한다. V1의1600px/0.82 상수를 바꾸지 않는다.

| 유형 | 처리 시작값 | 용량/가독성 기준 |
|---|---|---|
| 일반 사진/기본 | 긴 변1920px, WebP quality0.82~0.86 | 보통250~500KiB 목표. 크기 보장이 아니며 작은 원본은 불필요하게 키우지 않음 |
| 문서/스크린샷/작은 글자 | 긴 변2048px, WebP0.90 또는 무손실 WebP/PNG 비교 | 100% 확대에서 작은 글자/표 선을 판독할 수 있어야 함. bytes가 작다는 이유만으로 JPEG형 손실 강제 금지 |
| 투명 이미지 | alpha 유지 WebP 또는 PNG | 투명도/가장자리 보존 |
| 미리보기 | 긴 변640px WebP, 표시할 때 필요하면 생성 | 약30~80KiB 목표. 작고 이미 충분한 원본이면 variant 생략 |
| GIF/애니메이션 | 원본/애니메이션 유지 선택, 정지 썸네일 별도 | 움직임을 조용히 없애지 않음. 큰 파일은 명시적 선택/한도 안내 |

일반 처리본의 **2MiB 상한 후보**, 입력10MiB/디코드16MP·메모리 예산 후보를 별도로 시험한다. 품질 하향은 단계/하한을 두고 파일 크기만 맞추기 위해 읽을 수 없는 크기로 계속 줄이지 않는다. 상한을 넘으면 추가 축소 미리보기·고화질 선택·업로드 보류를 제공하며 로컬 사본은 보존한다. 서버의 최종 MIME/크기/차원/디코드 자원 제한도 필수다. 현재64KiB PoC 제한은 이런 제품 한도로 자동 변경된 것이 아니다.

EXIF 방향을 적용하고 불필요한 위치/카메라 메타데이터를 제거한다. ICC/sRGB/투명도와 PDF·Excel 내보내기 변환은 화면 비교로 확인한다. 기본은 **가독성 있는 보존 처리본1개**, 고해상 원본까지 매번 이중 업로드하지 않는다. 원본 보존을 사용자가 선택하면 추가 용량을 안내하고 별도 variant로 보관한다. 유일한 원본의 비가역 축소는 사용자 정책/미리보기 확정 전 자동 수행하지 않는다. 기존 V1 전환은 기본적으로 현재 저장 bytes를 보존해 추출하며 더 강한 재압축은 선택 기능으로 둔다.

온라인 DB에 binary를 저장하지 않는 것과 실물을 전혀 로컬 보관하지 않는 것은 다른 요구다. 새 온라인 이미지도 로컬 실물을 먼저 저장하고 업로드 실패 중 계속 사용한다. 온라인 원본/썸네일·PDF 내보내기마다 재압축/재업로드하는 순환을 만들지 않는다.

## 캐시·백업·GC·비용

원본/보존 처리본과 표시 캐시를 구분한다. 앱 재시작마다 변환하지 않고 blob hash+variant+policyVersion으로 캐시한다. 원격 이미지는 viewport에서 필요한 해상도만 읽고 LRU는 재생성 가능한 캐시만 정리한다. 완전 오프라인 보존 대상/미전송/충돌·로컬 독립 사본의 유일한 실물을 캐시처럼 삭제하지 않는다.

서버 물리 삭제는 현재 문서뿐 아니라 보존 snapshot·충돌 사본·trash/undo·미확정 업로드·복원 generation까지 참조가0이고 유예/재검사를 통과할 때만 한다. 단순 refcount 감소만으로 삭제하지 않는다. 공유 이미지가 있는 문서 하나를 지워도 다른 문서와 백업 복원이 유지돼야 한다. 계정/공간 삭제의 실제 범위는 별도 명시적 절차다.

용량은 hash별 **물리 bytes+variant+복구/전송 중 예약**으로 측정하고 논리 참조와 구분한다. blob 공유를 통한 절감률과 미리보기 추가 저장/egress를 함께 계측한다. 다운로드도 무료 quota에 포함한다. 예: 동일 처리본400KiB를20객체가 참조하고 썸네일50KiB를 공유하면 이론상450KiB(추가 index/백업/예약 제외), 독립 실물 복제면8,000KiB다. 이는 목표 모델 예시이지 실측 성과가 아니다. base64 자체의 약4/3 크기 오버헤드 제거 효과도 SQLite 페이지/index/파일시스템 overhead와 분리해 보고한다.

## 구현 전 결정·검증 관문

- 배포: V2 앱 식별자/프로그램·데이터·인증 경로/업데이트 피드 확정. V1 기존 DB+앱을 병행 실행해 원본/설정 hash·파일 연결이 보존되는지 확인.
- 프로필: 로컬 전용 빌드에서 cloud 환경변수/로그인/인터넷이 없어도 모든 기존 기능과 백업/복원이 동작. 네트워크 관측에서 기존 승인된 예외 외 온라인 요청0. 새 서버설정 없이 V1 회귀 검사 통과.
- 저장: 온라인 import/file rename/DB commit 각각의 종료·재시작에서 깨진 참조/원본 유실0. 기존 V1 이미지와 local DB는 그대로.
- 중복: 같은 bytes의 동시 업로드/주간↔업무 보드/노트 복제 시 물리1개, 개별 편집/삭제의 독립성, 다른 공간의 접근 차단. 잘못된 해시/bytes 거절.
- 복원/오프라인: 공유 자산을 포함한 백업 복원, 로그아웃/서버 장애/용량 초과 후 기기 원본 사용, 불완전 사본의 연결 해제 차단.
- 품질: 사진/표·작은 한글·투명도/큰 세로 스크린샷/GIF를 Windows/macOS에서 확대·PDF·Excel로 검토. 처리시간/peak RSS/저장 bytes·egress를 기록.
- 새 blob/reference/variant schema·quota/GC는 별도 migration/PoC 검토 후 구현. 현재 검토된 DB-only 패키지/기존 사용자 승인 범위에 자동 포함하지 않음.

추천 확정 순서: **환경/개발 접근 → 로컬 무영향 배포·저장 경계 → 자산/중복·quota schema → 품질 비교 시안/측정 → 개발 PoC → 실제 앱 통합**. 앱/사이트/가이드 다국어는 공통 언어 리소스로 관리하되 V1 저장 계약을 바꾸는 이유로 사용하지 않는다.
