# 32. 실제 Supabase 읽기 전용 점검 결과

## 결과

게시된 새 실행 환경에서 목적지 허용 적용과 개인 토큰 binding의 ready 상태를 확인했다. 새 HTTPS 요청으로 실제 프로젝트 조회에 성공했다. [비밀을 제외한 조회 증거](evidence/cloud-readiness-readonly.json)에 조회 시각·HTTP 상태·허용 필드만 보존한다. 로컬 샌드박스의 최초 연결은 EPERM으로 실패했고, 지원되는 외부 실행 경로에서 같은 프록시/TLS 설정으로 성공했다.

| 항목 | 실제 조회 결과 | 의미 |
|---|---|---|
| 프로젝트 | `Work Journey Board`, ref 일치 | 다른 프로젝트에 적용하지 않음 |
| 리전 | `ap-northeast-1` — 도쿄 | 사용자 확정 아시아 범위 충족 |
| 상태 | `ACTIVE_HEALTHY` | 조회 시점 정상. 장기 가용성/휴면 방지 검증은 아님 |
| 조직 플랜 | HTTP 403 | Free 여부 미확인. 토큰 불량으로 단정하지 않음 |
| 조직 entitlements | HTTP 403 | 계정별 기능 한도 미확인 |
| 프로젝트 추가상품 | HTTP 200, selected_addons 빈 배열 | 조회된 선택 추가상품 없음. Free/청구액 0원 증거와 구분 |
| Storage 파일 크기 상한 | 52,428,800 bytes — 50MiB | 파일 하나의 제한. 총 저장량/잔여량과 다름 |
| 이미지 변환 | 비활성 | 유료 변환을 전제로 설계하지 않음 |
| Auth custom SMTP | host/password 설정 없음 | 기본 시험 발송 설정. 외부 사용자 가입 제공 준비 안 됨 |
| Auth 이메일 rate limit | 시간당 2회 | 메일 발송 시험은 하지 않음 |
| Auth Site URL | `http://localhost:3000` | 현재 Vite 개발 포트1420 및 native callback에 맞춘 별도 설정 필요 |
| 이메일 확인 | mailer_autoconfirm false | 확인 절차를 우회하도록 변경하지 않음 |

HTTP 403인 두 조회의 원인을 특정 scope 이름이나 조직 역할로 단정하지 않는다. 프로젝트 GET/Auth/Storage 조회는 성공했으므로 조직 API 권한/접근 범위를 별도로 확인해야 한다. 월 0원 검증을 위해 토큰에 전체 권한을 추가하기보다 **대시보드에서 조직 Free 플랜과 Usage를 확인**하는 방법을 우선한다. 사용자에게 Free 여부를 요청했다. 대시보드 확인은 API 실측과 별도 근거로 표기한다.

DB 실제 사용량·Storage 총량·egress·Auth MAU·함수 사용량은 이번 응답에 없으므로 미측정이다. bucket 목록/공개 여부·테이블 RLS·SQL/cron·계정 복구 설정도 미검증이다. 선택 추가상품이 없다는 이유로 이 항목들을 통과 처리하지 않는다.

## 다음 최소 적용 묶음

[22문서](22-db-permission-sync-contract.md)의 전체 도메인을 한 번에 서버로 옮기지 않는다. 무료 조건 확인 후 다음 순서로 가상 데이터만 사용하는 작은 서버 시험을 구체화한다.

1. **로컬 실행 가능한 서버 migration/권한 시험.** 제품 DB18과 분리된 V2 전용 스키마, 공간·소유자·기기·명령 중복 방지·change cursor를 먼저 만든다. 한 개의 가상 텍스트 레코드 타입으로 시작하고 범용 JSON만으로 제품 도메인 검증이 끝났다고 보지 않는다. SQL 실행/변경 권한은 이번 읽기 토큰에 자동 추가하지 않는다.
2. **권한과 원자성.** 가상 계정 A/B·공간 A/B로 읽기/명령/자산의 교차 접근 거절, 위조 device/session·generation·중복 opId payload 변경 거절을 시험한다. 클라이언트 직접 쓰기는 막고 명령 함수는 고정 search_path·최소 EXECUTE 권한·행 잠금 안에서 상태/멱등 결과/change log를 함께 커밋한다. cursor는 공간 행 잠금 내 증가시켜 늦은 커밋 누락을 방지한다.
3. **인증 callback.** 먼저 로컬 가상 메일 수신 환경에서 Windows/macOS public client PKCE·state·기기 바인딩을 시험한다. callback 문자열은 실제 등록할 앱 스킴과 native 구현 검토 후 고정한다. 기존 Site URL을 추측한 주소로 덮어쓰지 않는다.
4. **아주 작은 private 자산 시험.** 전용 bucket·공간 소유권 정책·본문 hash/크기 제한·업로드 확정/회수 경계부터 검증한다. 공개 URL로 대체하지 않는다. 50MiB 최대 파일을 실제 시험 크기로 삼지 않는다.
5. **클라우드 적용 전 확인.** 적용 SQL·bucket/policy·callback·시험 계정 수·삭제/복구 범위·예상 사용량을 검토 가능하게 제시한다. Free/무료 잔여량을 확인한 뒤 해당 묶음만 적용하고 실제 두 계정 접근 차단/소형 왕복 시험을 기록한다.

Keep Alive는 기존 요구대로 하루 1회·한 행 갱신 설계를 유지한다. 실제 DB 권한과 migration이 준비된 뒤 별도 적용하며 이번 조회에서 job을 만들지 않았다. 내부 cron이 휴면 방지를 보장한다는 판정은 하지 않는다.

## 현재 판정

**접속·대상·아시아 리전 확인 완료 / 무료 플랜·잔여량 확인 대기 / 클라우드 쓰기 미실행.** 외부 사용자 메일 제공은 무료 SMTP/발신 도메인 조건까지 확인해야 한다. 팀 내부 시험과 공개 서비스 준비를 구분한다.

실제 GET은 프로젝트·해당 조직 메타데이터만 대상으로 했고 조직 회원·키·DB 내용은 조회하지 않았다. Auth 응답의 비밀 필드는 출력/파일 저장에서 제외했다. 토큰 권한 자체가 읽기 전용임을 이번 성공으로 증명한 것은 아니다. 제품·DB18·main·배포 및 P01~P22 전체 판정은 유지한다.
