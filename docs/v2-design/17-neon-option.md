# 17. Supabase 프로젝트 여유 없음에 따른 Neon 중심 재검토

2026-11-08 (KST) · 설계만 진행 · AWS 직접 운영 제외·무료/개인 요금·아시아 원칙 유지

**실제 사례 후속:** [18문서](18-existing-project-analysis.md)에 my-money-note의 구현/운영 기록을 분석했고 [19문서](19-supabase-env-consolidation.md)에 woori 개발 환경 대체와 Supabase branch 과금 조건을 확인했다. 현재 슬롯이 소진된 사실과 조건부 회수 가능성을 구분한다.

## 17.1 사용자 환경과 판단

사용자가 현재 Supabase 개인 사용한도2개를 모두 사용 중이라고 알려 주었다. **새 무료 Supabase 프로젝트가 남아 있다는 전제를 제거한다.** 이는 사용자 계정의 현재 제약이며 사업자의 모든 계정/요금제의 최신 공통 한도를 확인한 결과는 아니다.

Neon PostgreSQL을 우선 비교 후보에 추가한다. 사용자는 Neon ‘고려’를 요청했으며 사업자 선택·Neon 계정/프로젝트 생성이나 결제를 확정한 것은 아니다. 기존 Supabase 프로젝트를 지우거나 타 서비스와 무단 공용화해 한도를 확보하는 계획은 세우지 않는다.

## 17.2 대안 비교

| 구성 | 장점 | 추가 검증 | 현재 판단 |
|---|---|---|---|
| **A. Neon DB + 저비용 API + Auth + 객체 저장소** | PostgreSQL 도메인/관계·트랜잭션 재사용, 새 Supabase 무료 프로젝트 불필요 | DB 외 구성의 무료 한도·인증/메일·아시아 경로·연결 방식·복원 비용 | **우선 비교 추천**, 전체 조합 비용 확인 전 확정 금지 |
| B. Supabase 최소 유료 구성 | Auth/DB/Storage 운영 구성 수를 줄일 가능성 | 기존 계정/프로젝트 한도와 추가 프로젝트 실제 월 비용·초과 과금 확인 | 무료 신규 프로젝트를 가정하지 않는 비용 비교 후보 |
| C. Firebase 등 다른 관리형 | 대체 후보 | SQL 도메인 재설계·Storage/서버 결제 조건·읽기/쓰기 비용 | 예비 비교, 무료라고 단정하지 않음 |
| AWS 직접 구성 | 기존 검토안 | 사용자 지시로 현재 제외 | 다시 대안으로 끼워 넣지 않음 |

관리형 Neon이 내부적으로 특정 클라우드를 사용하더라도 사용자가 직접 AWS 서비스를 구성/운영하는 안과 구분한다. 현재 AWS 제외 원칙을 내부 공급망 전면 금지로 확대하지 않는다.

## 17.3 Neon을 쓸 때의 역할 분리

| 역할 | 우선 설계 후보 | 미확인 사항 |
|---|---|---|
| 구조화 데이터 | Neon PostgreSQL: 계정 매핑·공간·문서·revision/change log·멱등 키 | 계정/프로젝트 여유·무료 저장/연산·휴면/재개·아시아 실제 리전 |
| 인증 | Neon 제공 Auth 기능의 현재 조건 우선 확인, 맞지 않으면 외부 관리형 Auth | OTP·네이티브 세션/회수·메일·가격·처리 리전·복구. Neon DB 선택만으로 인증이 확정되지 않음 |
| Sync API | 저비용 서버리스 실행 환경(예: Cloudflare Workers 계열)을 조건부 비교 | Neon 연결 드라이버·트랜잭션·실행 제한·요금·처리 위치 |
| 이미지/보존본 | 비공개 객체 저장소(예: R2 계열)를 조건부 비교 | 무료/결제 조건·아시아 위치 보장·요청/다운로드·삭제/보관·서명 URL |
| 사이트/문서 | 무료 정적 호스팅 후보 | 공개 서비스 이용약관·도메인·배포 제한 |

위 이름은 후보이며 선택/가입 상태가 아니다. 모든 서비스를 추가하는 것이 목적이 아니다. Neon의 통합 기능이 요건을 충족하면 공급자 수를 줄인다. 별도 Auth를 쓰면 Neon DB+API+Auth+blob+메일의 전체 비용/운영량을 Supabase 최소 유료 구성과 비교한다.

개인용 무료 호스팅이라도 공개/상업 서비스 사용이 허용되는지 확인한다. 무료 DB를 쓰고 별도 서버를 상시 유료 운영하는 구조가 총비용 절감인지 따로 계산한다.

## 17.4 데이터·API 정합성

- 로컬 SQLite와 서버 PostgreSQL의 도메인/명령 계약은 유지한다. Neon으로 바꾼다고 클라이언트의 DB 파일을 서버에 올리는 구조로 바꾸지 않는다.
- 클라이언트에 DB 연결 문자열·관리자 키를 배포하지 않는다. Auth 증명→제품 accountId/device session→workspace 권한→명령 처리 경계를 유지한다.
- 서버리스 HTTP/pooled 연결에서 단일 명령의 데이터·change log·멱등성 기록을 한 트랜잭션으로 커밋할 수 있어야 한다. 여러 독립 HTTP 호출로 BEGIN/UPDATE/COMMIT을 흉내 내지 않는다.
- 선택한 드라이버의 비대화형 batch/transaction 또는 검증된 DB 함수 방식을 PoC한다. 기대 revision과 op 재전송의 경쟁 조건도 동일 트랜잭션에서 처리한다.
- 풀 연결의 세션 전역 사용자 컨텍스트에 의존하지 않는다. 테넌트 조건을 명령마다 검사하고 RLS/트랜잭션 로컬 컨텍스트를 쓸 경우 재사용 연결에서 다른 계정으로 누출되지 않도록 검증한다.
- DB 함수는 필요한 권한만 허용하고, security definer 등 권한 확대 방식은 안전한 search path/입력/소유권 검사를 검토한다.
- 원본 이미지/대형 snapshot base64를 Neon 행에 그대로 쌓지 않는다. 객체 저장소 원본+검증된 manifest 참조를 사용하고, DB·blob 모두 일관되게 복원되는지 확인한다.

## 17.5 scale-to-zero와 동기화 비용

무료/저가 연산은 사용량뿐 아니라 **DB가 깨어 있는 시간**의 영향을 받을 수 있다. 실제 과금 단위와 suspend 조건은 최신 플랜 확인 전 확정하지 않는다.

- health check/keep-alive가 DB 쿼리를 불필요하게 실행하지 않게 한다. 상시 서버/소켓/빈 polling이 절전을 막는지 측정한다.
- 연결된 공간 전체를 백그라운드에서 매5분 조회하는 기본값은 피한다. 화면에 활성인 공간에서만 주기 수신, 포커스/연결 복귀·수동 요청 때 수신, 로컬 수정 때 push를 기본 검증 후보로 둔다.
- 사용자2대가 번갈아 계속 사용하면 단일 사용자여도 DB가 오래 활성일 수 있다. 요청 수/byte 외에 active time·연산 단위·resume latency를 기록한다.
- 재개 지연을 ‘장애’로 오인해 중복 명령을 만들지 않는다. 동일 opId 재시도·timeout/재조회·로컬 대기 상태를 유지한다.
- 무료 보존/복원 시간창이나 DB branch를 사용자 백업 정책의 대체물로 단정하지 않는다. branch가 추가 저장/연산 한도를 소비하는지도 확인한다.
- 비용 절감을 위한 캐시/ETag는 변경 신호의 보조일 뿐이다. 캐시가 갱신되지 않아 영구 누락되지 않도록 정기적인 authoritative pull과 cursor 복구를 유지한다.

사용자가 요청한 기기 간 동기화 기능은 유지한다. 어떤 모드/주기를 기본으로 할지는 실제 연산·전송 한도와 지연을 확인한 뒤 결정하며 몰래 ‘백업 전용’으로 축소하지 않는다.

## 17.6 무료/개인 운영 확인표

확인 대상: ① Neon 계정의 실제 여유/플랜 ② DB 저장·연산·프로젝트/branch·휴면 ③ 아시아 리전 ④ 연결/드라이버·트랜잭션 ⑤ Auth/OTP/메일/회수 ⑥ 객체 저장 용량/요청/egress·아시아 보장 ⑦ API 실행·호스팅 약관/비용 ⑧ 백업/복원 ⑨ 합산 월 상한/초과 차단.

출발점: https://neon.com/pricing · https://neon.com/docs/introduction/regions · https://neon.com/docs 。실제 콘솔/공식 계약 확인이 필요하며 이 문서에 무료 수치를 채우지 않는다.

2026-11-08 공식 pricing/regions 페이지의 직접 확인을 시도했으나 현재 환경의 네트워크 프록시가403으로 차단했다. 최신 요금/리전·Neon Auth 조건을 확인한 것으로 처리하지 않는다. 계정별 실제 잔여량은 읽지 않았다.
