## 3. 버전 식별과 백업 생성

### 3-1. 새 파일명

예: `work-journey_2026-11-05_143012123_daily_app-v1.17.0_db-v14.db`

- 구성: 로컬 날짜 + 실제 시각(HHMMSSmmm) + 종류 + 백업을 생성한 앱 semver + **사본의 실제 DB 구조 번호**.
- 종류: `daily`, `monthly`, `manual`, `pre-migration-to-v15`, `pre-update`, `pre-import`, `before-restore`.
- `app-v1.17.0-rc.1`도 허용하는 명시적 semver 파서, 경로 구분자/상대 경로 거부. 파일명 포맷 파서를 한 곳에 두고 날짜·버전·종류 정렬에 재사용.
- 같은 밀리초 충돌 시 `_c1` 같은 제한된 숫자 접미사로 유일성을 확보한다. 실제 생성 시각을 미래로 바꾸지 않는다.
- 구조 변경 전 예: `..._pre-migration-to-v15_app-v1.17.0_db-v14.db`. v15는 **변경 목적지**, v14가 **보관된 사본의 실제 구조**다.
- 앱 버전은 백업 생성 프로그램의 버전이다. 이 DB를 마지막 편집한 앱의 버전으로 해석하지 않는다. 업데이트 전 닫힌 다른 공간의 사본도 동일 원칙.
- 파일명은 이력 표시용 메타데이터이며 무결성/호환성의 신뢰 근거가 아니다. 별도 매니페스트/새 DB 테이블을 추가하지 않는다. 사용자 DB 구조 변경도 불필요한 설계다.

### 3-2. 일관성과 교체

1. 기존 저장 마무리·저장소 배타 실행 안에서 원본의 `app_meta.schema_version`을 읽는다. 앱의 최신 지원 상수를 사본 버전으로 쓰지 않는다.
2. 고유 `.db.tmp`에 VACUUM INTO. quick_check + 사본 실제 구조 확인 후 원자적 최종 이름 변경.
3. 검증 완료된 최종 사본만 이력에 노출하고, 그 후에 기존 일일 사본 교체와 자동 보관 정리 실행. 생성 실패 때 기존 백업을 지우지 않는다.
4. 일일 슬롯은 ‘로컬 날짜 + 생성 앱 버전 + 실제 구조 버전’ 단위의 최신 사본 1개. 동일 슬롯만 새 사본 성공 후 교체하므로 같은 날 앱/구조가 바뀐 백업은 섞이지 않는다. 슬롯 교체는 보관 정책의 최신 최소 1개 규칙보다 먼저 수행한다.
5. 월간은 로컬 월의 첫 성공 사본을 유지한다. 수동/보호 사본은 매번 고유 이름으로 생성한다.
6. 시작·주기·종료·수동·구조 변경 전·가져오기 전·업데이트 전(닫힌 공간 포함)·복원 전·보조 백업 모두 적용. 원본이 파손된 복원 전 보존 파일은 구조를 못 읽으면 `db-unknown`으로 기록하고 자동 보호, ‘검사 불가’ 표시. 복원 전 파일은 기존처럼 이동·보존하며 별도 정상 백업으로 오인하지 않는다.
7. 검증 실패 잔여 임시 파일은 복원/이력에서 제외. 백업 폴더 이전 시 새·과거 형식 DB를 함께 복사한다.

## 4. 백업 이력과 복원

- 이력은 현재 존재하는 사본 목록이다. 삭제된 백업을 복원 가능한 이력으로 남기지 않는다. 마지막 정리 시각/개수/해제 용량과 실패 안내는 별도 요약으로 제공한다.
- 기본 최근순, 종류 필터(전체/자동/보호), 앱 버전·DB 구조·크기·파일명 표시. 긴 파일명은 상세에서 줄바꿈/복사, 목록은 버전 열을 유지하고 좁은 화면에서는 카드로 전환.
- 목록만 열 때 모든 DB를 열지 않는다. 새 이름의 버전은 ‘기록된 정보’, 선택 시 ‘실제 검사 결과’로 구분한다. 구형 사본도 선택하면 실제 DB 구조를 표시하되 앱 버전은 계속 ‘기록 없음’.
- 상세 비교: ‘현재 앱 1.17.0 · 지원 구조 v14’ ↔ ‘백업 생성 앱 1.16.0 · 실제 구조 v14’. 현재 열린 일지의 구조도 별도 표시. 파손 화면에서는 현재 일지 구조 ‘검사 불가’라도 앱의 지원 구조와 비교 가능.

| 실제 검사 결과 | 표시/복원 |
|---|---|
| 정상, 구조 = 지원 최신 | ‘현재 앱에서 복원 가능’ |
| 정상, 구조 < 지원 최신, 지원하는 마이그레이션 경로 있음 | ‘복원 후 구조 vN → v14로 갱신’ 사전 안내, 허용 |
| 구조 > 지원 최신 | ‘앱 업데이트 필요 · 이 앱은 v14까지 지원’과 복원 비활성 |
| 생성 앱이 더 최신이나 실제 구조는 지원 범위 | 앱 버전 차이 안내, 구조/필수 테이블 검사가 통과하면 허용 |
| 파일명 구조와 실제 DB 구조 다름 | ‘파일 정보 불일치’ 상세 표시, 복원 차단. 이름을 믿고 진행하지 않음 |
| quick_check 실패, 구조 누락/비정수/미지원 경로/필수 테이블 이상 | 원인별 표시, 복원 차단 |
| 구형 파일, 앱 버전 기록 없음 | 실제 DB 검사로 판정. 추정한 앱 버전을 표시하지 않음 |

복원 실행 직전에도 같은 검사를 다시 수행한다. 선택 후 파일이 바뀌면 검사/미리보기를 갱신하고 재선택을 요구한다. flush → 모든 저장소 detach → 일지 닫기 → 현재 파일 보존 → 백업 새 파일 복사 → 정상 열기/마이그레이션 순서를 재사용한다. 원본 복사 실패 시 보존 파일을 되돌리는 가드와 복원 취소 흐름 유지. 복원된 DB의 과거 설정으로 보관 정책이 갑자기 바뀌지 않도록 복원 직전 현재 정책을 보존하고, 성공 후 첫 자동 백업/정리 전에 다시 적용한다. 현재 정책을 읽을 수 없는 파손 복원에서는 생성은 허용하되 자동 삭제를 보류하고 정책 검토를 안내한다. 이 보류 상태는 PC의 공간별 설정에 남겨 재시작으로 사라지지 않게 한다. 임시 조회 드라이버는 반드시 닫고 원본 백업에 마이그레이션/설정 쓰기를 하지 않는다.

## 5. 보관 정책과 정리 알고리즘

### 5-1. 설정과 기본값

- 범위는 **현재 공간**. 상단에 공간 이름·폴더·전체 용량을 표시한다. 정책은 기존 `settings.backup` 안에 확장하고 구버전 필드를 호환 해석한다(스키마 마이그레이션 없이 JSON 설정 확장).
- 일일 기준: ‘개수’(기존) 또는 ‘기간’. 기간 7/14/30/90/180/365일, 사용자 숫자 1~3650일. 기간은 오늘 포함 N개 로컬 날짜, N=30이면 오늘부터 29일 전 날짜까지 보존. 앱을 안 켠 날도 기간에 포함되므로 ‘최근 30개’와 다름.
- 월간: 최근 0~120개. 기본 12, 0이면 월간 생성 끔. 기간이 지나도 별도 월간 사본으로 장기 복원 지점 유지.
- 용량: 끔 또는 256 MiB~100 GiB. UI 단위를 MiB/GiB로 명시. 전체 폴더 실제 사용량과 자동/보호/기타 사용량을 나눠 표시.
- 기존 사용자는 일일 14개·월간 12개와 주기 2시간 유지, 명시적으로 바꾸기 전 삭제 후보 확대 없음. 신규 설치 추천 기본은 일일 30일·월간 12개·용량 제한 끔. 기존 사용자도 ‘추천값’으로 초안만 변경 후 미리보기에서 확정.
- 자동 백업 시점/주기 및 보조 위치 최근 3개는 유지. 주 백업 용량 상한에 보조 폴더를 합산하거나 그 폴더를 함께 정리하지 않는다.

### 5-2. 삭제 후보 결정

1. 앱이 인식하는 정상 일일/월간 사본만 자동 정리 후보. 과거 형식도 기존 종류 규칙으로 포함한다. 알 수 없는 파일·다른 폴더·심볼릭 링크·불완전 정보 파일은 제외한다.
2. 보호 종류 5종과 최신 일일 최소 1개는 후보에서 제외한다. 파손/검사 불가/이름-구조 불일치로 확인된 파일은 자동 정리하지 않는다. 삭제 후보 DB는 실제 구조·무결성을 검사하고 읽기 실패/미지원 구조는 후보에서 제외한다. 삭제 직전에 후보의 타입·위치·크기/수정시각이 계획 때와 같은지 재확인한다.
3. 먼저 기간/개수에서 벗어난 일일과 개수 초과 월간 후보를 계산한다. 여러 버전 슬롯도 실제 DB 파일 개수/크기로 계산, 같은 이름 중복 없음.
4. 예상 폴더 용량이 상한보다 크면 남은 자동 사본을 오래된 순(동률은 파일명)으로 추가 후보화한다. **용량 기준이 기간/월간 개수보다 우선**하므로 기간 안의 사본도 지울 수 있음을 미리보기에서 설명한다.
5. 최신 일일·보호·기타 때문에 목표 용량 달성이 불가능하면 그 사본들을 보존하고 ‘자동 정리로 줄일 수 없는 용량’과 초과 이유를 표시한다. 백업 생성은 계속 허용한다. ‘최대 용량 보장’이라고 표현하지 않는다.
6. 자동 실행은 새 사본 검증 성공 뒤에만 수행. 디스크 부족으로 새 사본 생성 실패하면 기존 사본을 먼저 지우지 않고 공간 확보 안내.
7. 삭제는 기존 단일 TS 가드 + Rust 재검사를 유지·확장한다. 심볼릭 링크·경로 이탈·현재 일지·보호 사본 삭제를 양쪽에서 거부. 주기/수동/복원/이전/업데이트와 정리를 같은 공간 작업 락으로 직렬화하고 공간 전환 뒤 결과는 이전 공간에만 귀속한다.

### 5-3. 미리보기와 적용

- ‘정책 변경’ → 편집 → ‘정리 미리보기’. 현재 파일 기준 삭제 N개/회수 용량/유지 용량/보호 수/조건별 삭제 이유를 보여준다.
- 마지막 버튼 ‘정책 적용 및 N개 정리’. 0개면 ‘정책 적용’. 자동 정리로 실제 파일이 삭제되며 되돌릴 수 없음을 이 화면에서 명확히 안내한다.
- 적용 직전 다시 목록/통계를 계산한다. 후보가 바뀌면 새 미리보기를 보여주고 재확정, 이전 목록을 그대로 실행하지 않는다. 설정 저장 실패 시 삭제 없음. 저장 성공·일부 삭제 실패 시 성공분/실패분과 활성 정책을 명확히 보여준다.
- 현재 정책으로 ‘지금 정리’도 같은 미리보기/확정 경로를 사용한다. 무한 반복 자동 재시도 없음, 다음 성공 백업 시 다시 계획.
- 보호 사본은 이 UI에서 삭제하지 않는다. ‘백업 폴더 열기’로 위치·파일 크기를 확인한 후 사용자가 OS에서 관리한다. 앱 내 보호 사본 강제 삭제는 별도 기능으로 미룬다.

## 6. 시안 A — 현재 설정 화면 유지 + 통합 이력 창 (추천)

1. **설정 › 데이터·백업**: 기존 카드 위치 유지. 마지막 백업에 앱/구조 두 버전 표시, ‘백업 이력·복원’ 버튼. 보관 정책 요약 + ‘정책 변경’ + ‘지금 정리’. 사용량은 자동/보호/기타로 설명.
2. **통합 이력 창**: 왼쪽/상단 목록, 선택 상세와 버전 비교. 상태는 색+텍스트, 새 구조/구형/정보 없음도 같은 위치. 불필요한 배경 띠 없이 테두리·간격 중심.
3. **정책 편집/미리보기**: 보관 기준·월간·용량 입력 → 삭제 후보 목록 → 명시적 적용. 추천값 버튼과 취소 제공.
4. 버튼은 기존 16px 선형 모노그램 아이콘+문구. 모든 강조 띠/용량 표시선은 **직각**. 테마 3종과 키보드·초점·모달 닫기/복귀 지원.

대안 B: 별도 ‘백업 관리’ 전체 화면(이력에 넓은 공간, 설정 이동 증가). 대안 C: 지금처럼 설정과 복원 창 분리(변경은 적으나 정보/필터 중복). 기능 규모와 기존 화면 변경 최소화를 고려해 A 추천.

## 7. 승인 후 구현 순서와 검증

1. 공통 파일명/메타 타입·실제 구조 조회·모든 생성 경로·구형 읽기·TS/Rust 이름 가드. 현재 백업/복원/업데이트/폴더 이전 검사를 유지한다.
2. 순수 보관 계획 함수와 설정 호환 처리. 기간 경계·미래/이상 날짜·0개 월간·동률·용량 미달/초과·보호만으로 초과·가장 최신 1개·옛 파일·외부 파일·링크·변경된 후보 검증.
3. 설정/이력/복원/정리 미리보기 UI. 모든 복원 진입점과 진단 정보/백업 통계·보조 위치·옮기기 대응.
4. 데이터 안전 검증: 생성 실패·quick_check 실패·이름 변경 실패·용량 부족에서 기존 사본 보존, 정리 중 실패/경합, 복원 직전 재검사, 현재 파일 롤백, 여러 공간 3회 이상 왕복, 파손 화면 경로. TS 단위·Rust 테스트·Chromium/WebKit E2E.
5. 기능이 실제 구현되면 `data-spec`·복원 가이드·설정 사용법·장면12/대응표·실제 화면·HTML/PDF·릴리스 노트 동반 갱신. 빌드/타입/린트/포맷/전체 CI, 승인된 빌드 시 Windows 기본판+macOS.

## 8. 검토할 핵심

- A안(설정 유지+통합 이력 창), 파일명 버전 식별 방식.
- 추천 보관값: 일일 30일+월간12개, 용량 상한은 선택(기본 끔/활성화 시 2GiB).

### 시안 검증

로컬 Chromium에서 화면 전환, 구형/과거 사본 표시, 새 구조·정보 불일치 복원 차단, 보호 필터, 정리 미리보기, 추천 기본값, 개수/기간 전환과 좁은 설정 화면을 확인했다. 페이지 실행 오류 없음. 수치는 정적 예시이며 실제 파일 작업을 하지 않는다.

## 9. 구현 기록

- `backupIdentity.ts`에서 새/과거 이름을 읽고 생성 앱·실제 구조·날짜·종류를 구분한다. 파일은 고유 시각/충돌 번호로 만들며 같은 날짜·앱·구조의 정상 일일 사본만 새 사본 성공 후 교체한다. 파손된 월간 이름만 남았을 때도 새 정상 월간 생성을 허용한다.
- 생성 시 사본 구조를 검증하고, 복원에서는 실제 구조·필수 표/열·외래 키까지 확인한다. 실행 직전 크기/수정시각/구조의 변경을 재확인한다. 사용자 DB 구조는 v14 유지, 새 공간에만 추천 정책을 초기화하고 기존 공간은 개수 정책을 보존한다.
- 정책 확인→저장→정리를 저장소 배타 구간과 폴더 작업 순서로 직렬화한다. 복원/이전/자동 백업은 앱 작업 큐에서도 직렬화하며, 공간을 닫기 전에 남은 작업을 기다린다. 이전 공간의 작업이 새 공간에 실행되지 않게 한다.
- 보호·최신 정상·외부/불명/미지원 구조는 자동 정리하지 않는다. 원본 생성 실패 때 이전 사본을 먼저 삭제하지 않는다. 정책 저장 실패 시 삭제 없음, 일부 정리 실패는 결과 요약, 적용 직전 대상 변경은 재확인. 저장 이후 외부 변경으로 정리를 못 하면 자동 삭제를 보류한다.
- 복원 전 현재 정책은 PC의 공간별 설정으로 잠시 보존하고 성공 후 재적용한다. 파손 복원의 삭제 보류는 재시작/폴더 이전 뒤에도 유지한다. 보조 위치도 보류 중 생성은 계속하고 자동 삭제만 중단한다.
- 이력·복원과 정책 창에 키보드 초점 가두기/Escape/원래 단추 복귀를 제공한다. 정리 결과로 누른 단추가 사라져 초점이 body로 옮겨져도 Escape가 작동하도록 처리했다. 진행 중에는 닫기를 막는다.
- 실제 가상 기록 화면: `mockups/1105v13/implemented-{settings,history,policy,history-dark}.png`. 가이드 장면12/대응표/화면/HTML/PDF와 복원 안내·데이터 명세를 갱신했다. 새 의존성·외부 통신 없음.
- 제품 버전은 배포 전까지 1.16.0 유지. 릴리스 초안 `release-notes/v1.17.0-rc.1.md`, 향후 작업 브랜치 빌드는 Windows 기본판+macOS 대상이다.
